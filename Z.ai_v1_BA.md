# База знаний для подготовки к интервью бизнес-аналитика

**Профиль кандидата:** бизнес-аналитик с опытом ~2,5 года, телеком/ISP.
**Назначение:** справочник для подготовки и быстрого повторения перед собеседованием.

---

## Тема 1. SQL, BI-аналитика

### 1. Теория

#### 1.1. SQL — ядро работы аналитика

SQL (Structured Query Language) — декларативный язык запросов к реляционным БД. Бизнес-аналитик в телекоме обычно пишет запросы сам: выгрузить абонентов с просрочкой, посчитать ARPU по тарифам, собрать дашборд по оттоку. Поэтому на интервью SQL спрашивают всегда и почти всегда — с живой задачей.

**Базовый каркас запроса:**

```sql
SELECT   -- какие колонки вернуть
FROM     -- откуда (таблица или join-конструкция)
WHERE    -- фильтр строк ДО группировки
GROUP BY -- по каким полям группируем
HAVING   -- фильтр групп ПОСЛЕ группировки
ORDER BY -- сортировка результата
LIMIT    -- ограничение числа строк
```

Порядок выполнения внутри движка БД — **не совпадает** с порядком написания: `FROM → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT`. Это важно помнить, когда путаешь, можно ли использовать алиас из `SELECT` внутри `WHERE` (нельзя — на момент `WHERE` алиаса ещё не существует).

#### 1.2. Типы JOIN

Представь себе две таблицы: `subscribers` (абоненты) и `payments` (платежи). У каждого абонента может быть ноль, один или много платежей; у каждого платежа ровно один абонент.

- **INNER JOIN** — только строки, у которых есть совпадение в обеих таблицах. Если абонент не платил — он в результат не попадёт.
- **LEFT JOIN** — все строки из левой таблицы; если совпадения в правой нет, вместо её полей будут `NULL`. Удобно для «покажи всех абонентов и сумму их платежей (включая тех, кто не платил)».
- **RIGHT JOIN** — зеркально: все строки из правой. На практике почти не используется — обычно запрос переписывают через LEFT, поменяв таблицы местами.
- **FULL OUTER JOIN** — объединение: строки, где совпало, плюс строки без пары с обоих сторон (с `NULL` там, где пары нет).
- **CROSS JOIN** — декартово произведение: каждая строка левой соединяется с каждой строкой правой. Используется для генерации комбинаций (например, все тарифы × все регионы).
- **SELF JOIN** — не отдельный тип, а приём: таблица соединяется сама с собой. Удобно для иерархий (сотрудник → руководитель).

#### 1.3. GROUP BY и HAVING

`GROUP BY` собирает строки с одинаковыми значениями указанных полей в группы; к каждой группе можно применить агрегатные функции: `COUNT`, `SUM`, `AVG`, `MIN`, `MAX`.

`HAVING` — фильтр на уровне групп. Классическая задача: «найти абонентов, которые сделали больше 5 платежей за месяц».

```sql
SELECT subscriber_id, COUNT(*) AS payment_count
FROM payments
WHERE payment_date >= '2025-01-01'
GROUP BY subscriber_id
HAVING COUNT(*) > 5;
```

Запомни простое правило: фильтруем строки — `WHERE`; фильтруем группы — `HAVING`.

#### 1.4. Оконные функции

Оконные функции (window functions) считают агрегат или ранжирование **по набору строк, не схлопывая их** — у каждой строки остаётся её «личность», но рядом появляется значение «в контексте окна». Это инструмент, который отличает уверенного аналитика от новичка.

Синтаксис: `функция() OVER (PARTITION BY ... ORDER BY ... ROWS BETWEEN ... AND ...)`.

- `ROW_NUMBER()` — сквозной номер строки внутри партиции. Удобно выбрать «последний платеж каждого абонента».
- `RANK()` / `DENSE_RANK()` — ранг строки с учётом одинаковых значений (RANK пропускает номера, DENSE_RANK — нет).
- `LAG(col, n)` / `LEAD(col, n)` — значение из предыдущей / следующей строки. Идеально для «как изменился баланс по сравнению со вчерашним днём».
- `SUM/AVG/COUNT(...) OVER (...)` — нарастающий итог (running total) или скользящее среднее.

Пример: «последний платеж каждого абонента».

```sql
WITH ranked AS (
  SELECT subscriber_id, amount, payment_date,
         ROW_NUMBER() OVER (PARTITION BY subscriber_id ORDER BY payment_date DESC) AS rn
  FROM payments
)
SELECT subscriber_id, amount, payment_date
FROM ranked
WHERE rn = 1;
```

#### 1.5. Подзапросы vs CTE

Подзапрос (subquery) — запрос внутри запроса. CTE (Common Table Expression, `WITH name AS (...)`) — именованный подзапрос, который можно переиспользовать в основном запросе.

CTE почти всегда читается лучше, чем вложенный подзапрос, особенно когда логика многоступенчатая. В телекоме часто нужно сделать 3-4 шага: отфильтровать активных абонентов → присоединить их тарифы → посчитать сумму платежей → отфильтровать тех, у кого сумма выше порога. С CTE это читается как рецепт; с вложенными подзапросами — как матрёшка.

Рекурсивные CTE (`WITH RECURSIVE`) позволяют обходить иерархии: например, вывести все подразделения компании сверху вниз.

#### 1.6. Индексы

Индекс — это структура (обычно B-tree), которая позволяет БД быстро находить строки без полного сканирования таблицы. Аналогия: оглавление в книге — без него ищешь главу перелистыванием, с ним — за секунду.

Когда индекс помогает: точечные запросы по equality/диапазону (`WHERE subscriber_id = 123`), соединения (`JOIN ON ...`), сортировка (`ORDER BY`).
Когда не помогает или вредит: таблицы на 1000 строк (проще сканировать), частые `UPDATE/INSERT` (индекс тоже нужно перестраивать), запросы с `LIKE '%...'` (ведение по шаблону отключает индекс).

Составной индекс `(a, b, c)` работает для запросов по `a`, по `(a, b)`, по `(a, b, c)` — но **не** для запроса только по `b`. Это называется «правилом левого префикса».

#### 1.7. Нормализация (1NF–3NF) vs денормализация

Нормализация — процесс разбиения таблиц так, чтобы минимизировать избыточность и аномалии обновления.

- **1NF** — атомарность значений: в ячейке нет списков и массивов.
- **2NF** — нет частичных зависимостей от части составного первичного ключа (каждый неключевой атрибут зависит от всего ключа).
- **3NF** — нет транзитивных зависимостей: неключевой атрибут не зависит от другого неключевого.

В OLTP-системах (биллинг, CRM, биллинг телекома) обычно держат 3NF — данные меняются часто, важно не плодить копии.

Денормализация — обратный процесс: намеренно дублируем данные в одну плоскую таблицу ради скорости чтения. Это основа аналитических хранилищ (DWH): там данных терабайты, и JOIN по 6 таблицам на каждом запросе — роскошь.

#### 1.8. Транзакции и ACID

Транзакция — последовательность операций, которая выполняется как единое целое: либо все.commit, либо ни одна.

ACID — четыре свойства:

1. **Atomicity (атомарность)** — всё или ничего.
2. **Consistency (консистентность)** — после транзакции БД остаётся в согласованном состоянии (все ограничения, ключи, триггеры соблюдены).
3. **Isolation (изолированность)** — параллельные транзакции не мешают друг другу. Уровни изоляции: Read Uncommitted → Read Committed → Repeatable Read → Serializable. Чем выше, тем медленнее.
4. **Durability (долговечность)** — после commit изменения сохраняются даже при сбое питания.

В телекоме классический пример — списание платежа: нужно одновременно уменьшить долг абонента и увеличить кассу. Если упадёт посередине — деньги потеряются.

#### 1.9. BI-аналитика: OLTP vs OLAP

- **OLTP (Online Transaction Processing)** — системы, обслуживающие транзакции в реальном времени: биллинг, CRM, биллинг абонентов. Много коротких `INSERT/UPDATE`, текущие данные, схема в 3NF.
- **OLAP (Online Analytical Processing)** — системы аналитики: DWH, кубы, витрины. Много тяжёлых `SELECT` по историческим данным, схема «звезда» или «снежинка».

В телекоме типичный путь: биллинг (OLTP) → ETL в DWH (OLAP) → BI-инструмент рисует дашборд руководству.

#### 1.10. Схемы хранилища: звезда vs снежинка

- **Звезда (star schema):** в центре — одна таблица фактов (facts: платежи, звонки, сессии), вокруг неё — таблицы измерений (dimensions: абоненты, тарифы, даты, регионы). Измерения денормализованы — в одной таблице «регион» могут лежать и город, и область, и страна.
- **Снежинка (snowflake):** измерения нормализованы — «регион» ссылается на «город», тот на «область» и т.д. Меньше избыточности, но больше JOIN при запросе.

Звезда быстрее для аналитики (меньше JOIN), снежинка экономнее по месту и проще в сопровождении справочников. Большинство BI-дашбордов делают на звезде.

#### 1.11. Таблицы фактов и измерений

- **Таблица фактов (fact table)** — содержит измеримые события: платеж (sum, date, subscriber_id, channel_id), звонок (duration, from_subscriber, to_subscriber, tariff_id). Каждая строка — событие.
- **Таблица измерений (dimension table)** — описывает контекст события: кто (абонент), где (регион), когда (дата), по какому тарифу. Каждая строка — уникальный экземпляр справочника.

Особый случай — медленно меняющиеся измерения (Slowly Changing Dimensions, SCD). Тип 1: перезаписываем значение (старое теряем). Тип 2: создаём новую строку с датами действия — сохраняем историю. Для телекома важно: абонент сменил тариф — мы хотим знать, сколько он платил ДО смены и ПОСЛЕ.

#### 1.12. ETL vs ELT

- **ETL (Extract-Transform-Load):** выгрузили из источника → трансформировали на стороне ETL-инструмента → загрузили готовое в DWH. Классика, удобно когда источник слабый, а целевая СУБД простая.
- **ELT (Extract-Load-Transform):** выгрузили сырые данные → загрузили в DWH как есть → трансформировали уже SQL-запросами внутри DWH. Работает когда DWH мощный (ClickHouse, Snowflake, BigQuery).

Современный тренд — ELT, потому что облачные колоночные БД позволяют трансформации прямо в хранилище быстрее, чем отдельный ETL-движок.

#### 1.13. BI-инструменты

Зарубежные: **Power BI** (Microsoft, очень популярен в корпоративном сегменте), **Tableau** (глубокая визуальная кастомизация), **Qlik** (ассоциативная модель), **Superset** (open-source, Python-friendly).

Российский рынок: **DataLens** (Яндекс, глубоко интегрирован с Yandex Cloud), **Apache Superset** в self-hosted варианте, **Visiology** (российская платформа для enterprise), **FineBI** (китайский, активно заходил в РФ), **Tantor** и другие. В телекоме (МТС, Билайн, МегаФон, Tele2) — смесь self-hosted Superset и проприетарных решений; DataLens часто встречается в продуктах, завязанных на экосистему Яндекса.

#### 1.14. Метрики, KPI и дизайн дашборда

Метрика — измеримый показатель (например, «количество активных абонентов»). KPI — метрика, у которой есть цель и горизонт («увеличить ARPU до 450 ₽/мес к концу квартала»).

Принципы дизайна дашборда:

1. **Один дашборд — одна аудитория и одна задача.** Дашборд для CEO и для аналитика — это два разных дашборда.
2. **Сверху — итоги (KPI-карточки), ниже — детализация (таблицы, графики).**
3. **Сначала ответ, потом вопрос:** главная цифра должна быть видна за 5 секунд.
4. **Группировка по принципу Z-образного чтения** — слева сверху направо вниз.
5. **Минимум цветов.** Цвет — только чтобы что-то подчеркнуть (рост/падение, отклонение от нормы).
6. **Фильтры и срезы** — должны быть очевидны и согласованы.
7. **Никаких 3D-круговых диаграмм** и графиков ради графиков.

### 3. Практика

**1. Чем INNER JOIN отличается от LEFT JOIN? Когда выбираешь каждый?**

> INNER JOIN возвращает только строки с совпадением в обеих таблицах. LEFT JOIN возвращает все строки левой таблицы, а при отсутствии совпадения в правой — подставляет NULL. Я выбираю INNER, когда мне нужны только те записи, у которых точно есть пара — например, «абоненты, у которых есть хотя бы один платёж за период». LEFT — когда нужно сохранить всех, включая тех, у кого пары нет: «все абоненты и сумма их платежей, включая неплательщиков». На практике в телекоме LEFT используется чаще, потому что бизнес почти всегда хочет видеть «молчунов» и «нулевиков», а не только активных.

**2. В чём разница между WHERE и HAVING?**

> WHERE фильтрует строки ДО группировки, HAVING — группы ПОСЛЕ. Логика простая: если условие можно проверить на отдельной строке — это WHERE (например, `payment_date >= '2025-01-01'`). Если условие относится к агрегату по группе — это HAVING (например, `COUNT(*) > 5`). На интервью часто ловят на попытке написать `WHERE COUNT(*) > 5` — это синтаксическая ошибка, потому что на момент WHERE групп ещё не существует.

**3. Объясни, что делает оконная функция и чем отличается от GROUP BY.**

> GROUP BY схлопывает строки группы в одну, возвращая агрегат. Оконная функция считает агрегат или ранг по набору строк, но строки не схлопывает — у каждой остаётся её идентичность, а рядом появляется значение «в контексте окна». Например, если мне нужен список всех платежей абонента с рангом «самый большой платёж = 1» — оконная функция даёт это в один проход. Через GROUP BY пришлось бы сначала найти максимум, потом join'ить обратно. Также оконные функции позволяют LAG/LEAD — сравнивать строку с соседней, что в GROUP BY в принципе невозможно.

**4. Что такое CTE и зачем его использовать вместо подзапроса?**

> CTE — это именованный подзапрос, объявляемый через `WITH name AS (...)` в начале запроса. Главное преимущество — читаемость: сложную логику можно разбить на шаги, как рецепт. Подзапрос, особенно вложенный в три уровня, читается как матрёшка — нужно держать в голове контекст каждого уровня. CTE можно переиспользовать в основном запросе сколько угодно раз — подзапрос пришлось бы дублировать. Ещё CTE может быть рекурсивным (`WITH RECURSIVE`), что позволяет обходить иерархии — например, вывести все подразделения компании сверху вниз.

**5. Напиши запрос: найти топ-3 тарифа по выручке за последний месяц.**

```sql
SELECT t.tariff_name, SUM(p.amount) AS revenue
FROM payments p
JOIN subscribers s ON p.subscriber_id = s.subscriber_id
JOIN tariffs t     ON s.tariff_id = t.tariff_id
WHERE p.payment_date >= date_trunc('month', CURRENT_DATE) - INTERVAL '1 month'
  AND p.payment_date <  date_trunc('month', CURRENT_DATE)
GROUP BY t.tariff_name
ORDER BY revenue DESC
LIMIT 3;
```

> Здесь я присоединяю платежи к абонентам и тарифам, фильтрую предыдущий календарный месяц через `date_trunc`, группирую по тарифу, сортирую по убыванию выручки и беру первые три. Если бы тарифов было много и запрос шёл часто — добавил бы индекс на `payments(subscriber_id, payment_date)`.

**6. Напиши запрос: для каждого абонента вывести его последний платёж (дата и сумма).**

```sql
WITH ranked AS (
  SELECT subscriber_id, amount, payment_date,
         ROW_NUMBER() OVER (PARTITION BY subscriber_id ORDER BY payment_date DESC) AS rn
  FROM payments
)
SELECT subscriber_id, amount, payment_date
FROM ranked
WHERE rn = 1;
```

> Это классическая задача на оконную функцию. Я партиционирую по абоненту, сортирую по дате убыванию, нумерую строки и беру первую. Альтернатива через `DISTINCT ON` работает в PostgreSQL, но не переносима. `LEFT JOIN` с подзапросом max(date) тоже сработает, но если у абонента есть два платежа в одну дату — результат может задвоиться, и тогда приходится добавлять tie-breaker.

**7. Напиши запрос: посчитать нарастающий итог платежей по дням за текущий месяц.**

```sql
SELECT payment_date::date AS day,
       SUM(amount) AS daily_total,
       SUM(SUM(amount)) OVER (ORDER BY payment_date::date
                              ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running_total
FROM payments
WHERE payment_date >= date_trunc('month', CURRENT_DATE)
GROUP BY payment_date::date
ORDER BY day;
```

> Сначала группирую по дате и считаю дневную сумму. Потом применяю оконную функцию `SUM(SUM(amount)) OVER (...)` с рамкой «от начала до текущей строки» — это и даёт нарастающий итог. Важный нюанс: внутренний `SUM` — это агрегат, внешний `SUM` — оконный над результатом агрегата; такая конструкция валидна.

**8. Что такое индекс и в каких случаях он НЕ сработает?**

> Индекс — это структура (обычно B-tree), которая позволяет БД искать строки не полным сканированием, а быстрым спуском по дереву. Не сработает или сработает неэффективно в нескольких случаях: функция над колонкой в WHERE (`WHERE LOWER(name) = 'ivan'` — нужно функциональный индекс), `LIKE '%...'` (ведущий wildcard отключает B-tree), нарушение левого префикса составного индекса (индекс на `(a, b, c)` не поможет запросу по `b`), маленькая таблица (оптимизатор решит, что проще сканировать), либо когда селективность низкая (например, фильтр возвращает 80% таблицы — индекс только добавит накладные расходы).

**9. Объясни разницу между OLTP и OLAP. В каком из них мы работаем в биллинге, а в каком — в DWH?**

> OLTP — это транзакционные системы с короткими, частыми операциями записи и чтения одной строки: биллинг абонентов, CRM, OSS. Схема в 3NF, данные текущие, обновляемые. OLAP — аналитические системы с тяжёлыми чтениями по большим массивам исторических данных: DWH, кубы, витрины. Схема «звезда» или «снежинка», данные в основном дописываются, не обновляются. В телекоме биллинг — это OLTP: каждый платёж, каждая CDR-запись (call detail record) — это INSERT. Аналитические дашборды руководства работают поверх DWH — это OLAP. Между ними стоит ETL/ELT-пайплайн, который перекладывает данные из одного мира в другой.

**10. В чём разница между звездой и снежинкой? Что выберешь для дашборда по выручке и почему?**

> В звезде измерения денормализованы: одна таблица «регион» может содержать город, область и страну в одной строке. В снежинке измерения нормализованы: «регион» ссылается на «город», тот на «область» и т.д. Звезда даёт меньше JOIN при запросе — быстрее читается, но больше избыточности. Снежинка компактнее и проще в сопровождении справочников, но каждый запрос тянет дополнительный JOIN. Для дашборда по выручке я бы взял звезду: читается часто, переписывается редко, и каждый JOIN по большой таблице фактов — это на секунды дольше. Снежинку имеет смысл там, где справочники меняются часто и есть риск аномалий обновления.

**11. Что такое ACID? Приведи пример из телекома, где нарушение ACID создаёт проблему.**

> ACID — это четыре свойства транзакции: Atomicity (всё или ничего), Consistency (БД остаётся в согласованном состоянии), Isolation (параллельные транзакции не мешают), Durability (commit сохраняется при сбое). Пример: списание платежа. Абонент кладёт 500 ₽ на счёт. Транзакция должна одновременно уменьшить долг в биллинге, увеличить баланс абонента, записать движение в кассу и создать CDR-запись. Если упадёт посередине — мы получим либо «деньги списаны, но не зачислены» (абонент злится), либо «зачислены, но в кассе не отражены» (бухгалтерия злится). Atomicity гарантирует, что этого не произойдёт. Isolation — что если два платежа от одного абонента придут одновременно, оба корректно отразятся, а не перезатрут друг друга.

**12. Какие метрики ты бы включил в дашборд по оттоку абонентов для директора по продукту?**

> Я бы строил от итогов к детализации. Наверху — две KPI-карточки: месячный churn rate в % и абсолютное число ушедших за месяц. Ниже — тренд за 12 месяцев с целевой линией. Дальше — разбивка по ключевым срезам: тариф (какие тарифы теряют больше), срок жизни абонента (когортный анализ: 1-й месяц, 3-й, 6-й, 12-й), причина ухода (если есть классификация: цена, конкурент, качество связи, переезд). Отдельный блок — предиктивный: список абонентов с высоким риском ухода в ближайшие 30 дней (если есть ML-модель). И фильтры по региону и сегменту (B2C / B2B). Цвет — только красным для негативных отклонений; не нужно раскрашивать каждую колонку.

### 4. Типичные ошибки и на что смотрят интервьюеры

**Частые ошибки кандидатов:**

- Путают порядок выполнения SQL с порядком написания — пишут алиас из `SELECT` в `WHERE`.
- Не понимают, что `LEFT JOIN` без проверки `IS NULL` в правой таблице ведёт себя как `INNER`, когда в фильтре правой таблицы стоит условие.
- Думают, что оконная функция и GROUP BY — это одно и то же. Это не так: GROUP BY схлопывает, оконная — нет.
- Называют «индексом» что угодно — первичный ключ, ограничение, статистику. Индекс — это конкретная структура.
- Говорят «нормализация — это хорошо, всегда нормализуем до 3NF» — забывают, что в DWH умышленно денормализуют.
- На задачу по BI-дизайну сразу начинают перечислять графики, не спросив «кто зритель и какое решение он принимает».
- Забывают про российский рынок BI-инструментов: DataLens, Visiology. В телекоме сейчас это актуально из-за импортозамещения.

**Сильный vs слабый ответ:**

| Что спрашивают | Слабый ответ | Сильный ответ |
|---|---|---|
| Чем LEFT JOIN отличается от INNER? | «LEFT возвращает все строки левой таблицы». | «LEFT возвращает все строки левой, подставляя NULL при отсутствии пары. INNER — только совпавшие. Я выбираю LEFT, когда важно сохранить нули и молчунов, что в телекоме бывает почти всегда». |
| Объясни оконную функцию | «Это как агрегат, но по окну». | «Оконная функция считает значение по набору строк, не схлопывая их. Например, ROW_NUMBER позволяет выбрать последний платёж каждого абонента без self-join». |
| Что такое ACID? | Перечисляет 4 слова без объяснения. | Называет все четыре + пример «платеж списан, но не зачислен» — это нарушение Atomicity. |

**На что смотрит интервьюер:**

- Понимает ли кандидат порядок выполнения SQL или просто заучил синтаксис.
- Может ли выбрать тип JOIN осознанно, а не «потому что так в туториале».
- Различает ли аналитическую и транзакционную нагрузку — это базовое разделение для BA в телекоме.
- Умеет ли спроектировать дашборд под аудиторию, а не «нарисовать красивые графики».

> **Телеком-акцент:** в интервью на BA в телекоме почти всегда спрашивают про CDR (Call Detail Record), про ARPU/ARPA, про churn rate, про биллинговые циклы. Если доведётся говорить про BI — упомяни, что данные из биллинга текут в DWH, а оттуда в дашборды; это закрытый цикл, который ты понимаешь целиком.

## Тема 2. API

### 1. Теория

#### 1.1. Что такое API

API (Application Programming Interface) — контракт, по которому одна программа обращается к другой. Для бизнес-аналитика API — это почти то же самое, что техническое задание на интеграцию: описано, что можно запросить, какие данные прислать, что вернётся, какие бывают ошибки. BA не пишет код API, но пишет требования к нему: какие эндпоинты нужны бизнесу, какие поля у запроса и ответа, какие статусы возвращать.

#### 1.2. REST — самый распространённый стиль

REST (Representational State Transfer) — набор архитектурных ограничений, описанных Роем Филдингом в 2000 году. Не протокол, не стандарт — именно стиль. Большинство «REST API» в индустрии — это HTTP API, более-менее соблюдающий ограничения REST.

Шесть ограничений REST:

1. **Client-Server** — клиент и сервер разделены; клиент не знает, как устроено хранилище сервера.
2. **Stateless** — каждый запрос содержит всю информацию для его обработки. Сервер не хранит состояние сессии между запросами.
3. **Cacheable** — ответ должен явно указывать, можно ли его кэшировать и на сколько.
4. **Uniform interface** — единый способ взаимодействия: ресурсы идентифицируются URL, манипуляции через представления (representations), ссылки на связанные ресурсы (HATEOAS — на практике почти никто не соблюдает).
5. **Layered system** — клиент не знает, общается ли он с конечным сервером или с промежуточным (балансировщиком, CDN, шлюзом).
6. **Code-on-demand (опционально)** — сервер может отдать исполняемый код (JS), который клиент выполнит.

На интервью достаточно назвать первые четыре и понимать, что stateless — ключевое.

#### 1.3. HTTP-методы и их семантика

| Метод | Назначение | Идемпотентность | Безопасность | Тело запроса |
|---|---|---|---|---|
| GET | Получить ресурс | Да | Да | Нет |
| POST | Создать ресурс / запустить действие | Нет | Нет | Да |
| PUT | Заменить ресурс целиком (создать, если нет) | Да | Нет | Да |
| PATCH | Частично изменить ресурс | Нет (обычно) | Нет | Да |
| DELETE | Удалить ресурс | Да | Нет | Нет (обычно) |
| HEAD | Как GET, но без тела | Да | Да | Нет |
| OPTIONS | Какие методы поддерживаются | Да | Да | Нет |

**Идемпотентность** — свойство: повторный вызов того же запроса даёт тот же результат, что и первый. `PUT /users/5` с одним и тем же телом можно дёргать 10 раз — пользователь будет в одном и том же состоянии. `POST /users` 10 раз — создаст 10 пользователей.

**Безопасность (safe)** — метод не меняет состояние сервера. GET/HEAD/OPTIONS безопасны, остальные — нет. Это важно для кэширования и для семантики: поисковые роботы делают только GET.

#### 1.4. HTTP-статусы

Группы:

- **1xx Informational** — редко встречаются.
- **2xx Success** — `200 OK`, `201 Created` (создано, обычно с `Location`-заголовком), `204 No Content` (успех, но без тела — типично для DELETE).
- **3xx Redirection** — `301 Moved Permanently`, `304 Not Modified` (кэш валиден).
- **4xx Client Error** — `400 Bad Request` (общий), `401 Unauthorized` (не авторизован, нет токена), `403 Forbidden` (авторизован, но прав не хватает), `404 Not Found`, `409 Conflict` (конфликт состояния), `422 Unprocessable Entity` (тело корректно синтаксически, но семантически невалидно), `429 Too Many Requests`.
- **5xx Server Error** — `500 Internal Server Error`, `502 Bad Gateway`, `503 Service Unavailable`, `504 Gateway Timeout`.

Частая ошибка кандидатов: путают 401 и 403. Запомни: **401 — «я тебя не знаю»** (нет или неверный токен), **403 — «я тебя знаю, но тебе нельзя»** (прав не хватает).

#### 1.5. Структура запроса и ответа

HTTP-запрос состоит из:

1. **Стартовая строка**: метод + URL + версия протокола (`POST /api/v1/orders HTTP/1.1`).
2. **Заголовки (headers)**: метаданные — `Content-Type`, `Authorization`, `Accept`, `X-Request-ID`. Заголовки — это пары ключ-значение.
3. **Пустая строка-разделитель**.
4. **Тело (body)**: данные запроса, обычно JSON.

HTTP-ответ симметричен: стартовая строка с кодом состояния, заголовки, пустая строка, тело.

Ключевые заголовки для BA:

- `Content-Type: application/json` — формат тела запроса/ответа.
- `Authorization: Bearer <token>` — аутентификация.
- `Accept: application/json` — какой формат клиент готов принять.
- `Cache-Control` — правила кэширования.
- `X-Request-ID` / `X-Correlation-ID` — идентификатор запроса для трассировки (важно в микросервисах).

#### 1.6. Аутентификация

- **API key** — простая строка, передаётся в заголовке (`X-API-Key`) или в query. Минус — кто знает ключ, тот и есть «пользователь»; сложно отзывать права. Подходит для server-to-server с доверенными партнёрами.
- **Basic Auth** — логин/пароль, закодированные в Base64. Не используйте без HTTPS.
- **OAuth2** — фреймворк авторизации, позволяющий стороннему приложению получить ограниченный доступ без передачи пароля. Пользователь логинится у провайдера, провайдер выдаёт access_token (короткоживущий) и refresh_token (долгоживущий). Сценарий «войти через Яндекс/Google» — это OAuth2.
- **JWT (JSON Web Token)** — компактный самодостаточный токен в формате `header.payload.signature`. Сервер подписывает токен, клиент прикладывает его к каждому запросу. Сервер проверяет подпись — без обращения к БД. Минус: отозвать выпущенный JWT до истечения срока нельзя (только чёрные списки или короткий TTL).

На практике комбинация: OAuth2 для первичной авторизации → выпускает JWT → клиент ходит с JWT.

#### 1.7. Пагинация

Когда коллекция большая (`GET /subscribers` может вернуть миллионы), её режут на страницы. Варианты:

- **Offset/Limit**: `?offset=20&limit=10`. Простой, но при параллельной записи «пляшут» результаты — на третьей странице может попасться строка с первой.
- **Page/Size**: `?page=2&size=10`. То же самое, удобнее для UI.
- **Cursor-based (keyset)**: `?cursor=eyJpZCI6MTIzfQ&limit=10`. Сервер возвращает курсор на следующую страницу. Стабилен при параллельной записи, но сложнее в реализации.

В телекоме, где абонентов миллионы, обычно используют cursor-based для внутренних API и offset-based — для внешних UI.

#### 1.8. Версионирование

Когда API меняется несовместимо (убрали поле, поменяли тип), нужно версионировать, чтобы не сломать существующих клиентов. Способы:

- **В URL**: `/api/v1/orders`, `/api/v2/orders`. Самый распространённый, самый явный.
- **В заголовке**: `Accept: application/vnd.company.v2+json`. Чистый URL, но сложнее тестировать и кэшировать.
- **В query**: `?version=2`. Редко.

Стандарт индустрии — версия в URL.

#### 1.9. Rate limiting

Ограничение числа запросов от клиента в единицу времени. Защищает сервис от перегрузки и злоупотреблений. Реализуется на API gateway. Заголовки ответа:

- `X-RateLimit-Limit` — лимит.
- `X-RateLimit-Remaining` — сколько осталось.
- `X-RateLimit-Reset` — когда счётчик сбросится (Unix timestamp).

При превышении — `429 Too Many Requests`, опционально с заголовком `Retry-After`.

#### 1.10. SOAP vs REST vs GraphQL

| Аспект | SOAP | REST | GraphQL |
|---|---|---|---|
| Протокол | HTTP, SMTP, JMS | HTTP | HTTP (обычно POST на один эндпоинт) |
| Формат | XML | Любой (обычно JSON) | JSON |
| Контракт | WSDL | OpenAPI (опционально) | GraphQL Schema |
| Стиль | RPC, операции | Ресурсы и HTTP-методы | Запросы с указанием нужных полей |
| Идемпотентность | Заложена в стандарт | Зависит от метода | Зависит от mutation |
| Сложность | Высокая, тяжёлый XML | Средняя | Средняя |
| Under/Over-fetching | Возможен | Возможен | Решён — клиент просит ровно нужное |
| Где встречается | Enterprise, банкинг, телеком-биллинг | 90% современных API | Web/Mobile с разными экранами |

SOAP до сих пор жив в телекоме и банкинге: OSS/BSS системы, интеграция с биллингом оператора, часто через SOAP. REST — стандарт для новых веб- и мобильных API. GraphQL — реже, обычно в продуктах с web+mobile клиентами, где каждый экран хочет своё подмножество полей.

#### 1.11. OpenAPI / Swagger

OpenAPI (ранее Swagger Specification) — стандарт описания REST API в виде YAML/JSON. Один файл описывает все эндпоинты, методы, параметры, тела запросов/ответов, коды ошибок, модели аутентификации. На основе файла генерируется:

- интерактивная документация (Swagger UI, Redoc);
- клиентские SDK для разных языков;
- серверные стабы;
- моки для тестирования.

Для BA OpenAPI — рабочий инструмент: ты можешь прочитать контракт, понять, какие эндпоинты есть, какие поля обязательны, какие коды возвращаются. И можешь написать драфт контракта, оставив разработчикам только уточнить крайние случаи.

#### 1.12. Как BA пишет API-контракт

Алгоритм:

1. Понять бизнес-сценарий: что хочет клиент, что должно произойти на сервере.
2. Определить ресурсы и операции: какие сущности, какие CRUD-действия нужны.
3. Для каждой операции описать: метод, путь, заголовки, тело запроса, тело ответа, коды ошибок.
4. Согласовать с разработчиками: достаточно ли данных для реализации, нет ли пропущенных кейсов.
5. Зафиксировать в OpenAPI-файле или в Confluence с примерами.
6. Согласовать с потребителем API (frontend, partner) — все ли поля понятны, не нужно ли ещё чего-то.

### 2. Глоссарий и термины

| Русский термин | English | Определение |
|---|---|---|
| Аутентификация | Authentication | Проверка, кто обращается к системе. |
| Безопасный метод | Safe method | HTTP-метод, не меняющий состояние сервера (GET, HEAD, OPTIONS). |
| Версионирование | Versioning | Управление несовместимыми изменениями API через явное указание версии. |
| Идемпотентность | Idempotency | Свойство: повторный запрос даёт тот же результат, что и первый. |
| Курсор | Cursor | Маркер позиции в коллекции для cursor-based пагинации. |
| Ограничение запросов | Rate limiting | Лимит числа запросов клиента в единицу времени. |
| Payload (тело) | Body / Payload | Данные запроса или ответа, отделённые от заголовков. |
| Пагинация | Pagination | Разбиение большой коллекции на страницы. |
| Ресурс | Resource | Идентифицируемая сущность API (subscriber, order, payment). |
| Состояние без сохранения | Statelessness | Принцип: каждый запрос самодостаточен, сервер не хранит сессию. |
| Токен доступа | Access token | Короткоживущий токен, прикладываемый к запросам для авторизации. |
| Эндпоинт | Endpoint | URL, по которому доступна операция API. |
| Авторизация | Authorization | Проверка прав субъекта на действие. |
| GraphQL | GraphQL | Язык запросов, где клиент сам описывает нужные поля. |
| HTTP-статус | HTTP status | Код состояния ответа: 1xx–5xx. |
| HATEOAS | HATEOAS | Hypermedia as the Engine of Application State — ссылки на связанные ресурсы в ответе. |
| JWT | JSON Web Token | Самодостаточный подписанный токен: header.payload.signature. |
| OAuth2 | OAuth 2.0 | Фреймворк делегированной авторизации. |
| OpenAPI | OpenAPI Specification | Стандарт описания REST API в YAML/JSON. |
| REST | Representational State Transfer | Архитектурный стиль с шестью ограничениями Филдинга. |
| SOAP | Simple Object Access Protocol | Протокол обмена XML-сообщениями, чаще всего поверх HTTP. |
| WSDL | Web Services Description Language | Язык описания SOAP-сервисов. |

### 3. Практика

**1. Что такое REST и какие у него ключевые ограничения?**

> REST — это архитектурный стиль, описанный Роем Филдингом в 2000 году. Это не протокол и не стандарт, а набор ограничений. Ключевых ограничений шесть: клиент-сервер, statelessness (каждый запрос самодостаточен, сервер не хранит сессию), cacheable (ответ явно помечается как кэшируемый или нет), uniform interface (ресурсы идентифицируются URL, манипуляции через представления), layered system (клиент не знает, общается ли с конечным сервером или с промежуточным), и опциональный code-on-demand. Из этих на практике самое важное — stateless: именно оно позволяет горизонтально масштабировать REST-сервис, потому что любой сервер может обработать любой запрос.

**2. Объясни разницу между 401 и 403.**

> 401 Unauthorized — это «я тебя не знаю»: нет токена, токен истёк, токен невалидный. 403 Forbidden — «я тебя знаю, но тебе сюда нельзя»: пользователь аутентифицирован, но у него нет прав на этот ресурс. На практике: 401 возвращается middleware аутентификации до того, как запрос дойдёт до бизнес-логики; 403 — уже в бизнес-логике, после проверки прав. Запомнить просто: 401 — «кто ты?», 403 — «ты не должен это делать».

**3. Что такое идемпотентность? Какие HTTP-методы идемпотентны?**

> Идемпотентность — свойство операции: повторный вызов даёт тот же результат, что и первый. Идемпотентны GET, PUT, DELETE, HEAD, OPTIONS. Не идемпотентны POST и (обычно) PATCH. Идемпотентность критична для надёжной retry-логики: если клиент не уверен, дошёл запрос или нет, он может безопасно повторить идемпотентный. Для POST так делать нельзя — можно задвоить создание сущности. Поэтому для критичных операций часто вводят идемпототен-ключ (Idempotency-Key header), который сервер использует для дедупликации.

**4. Чем PUT отличается от PATCH?**

> PUT заменяет ресурс целиком: если какое-то поле не указано в теле — оно становится null или дефолтным. PATCH меняет ресурс частично: только указанные поля обновляются, остальные остаются нетронутыми. PUT идемпотентен, PATCH — нет (по стандарту, хотя на практике зависит от реализации). Пример: у абонента 5 полей. PUT отправляет все 5 — даже если меняешь только имя. PATCH отправляет только `{"name": "Ivan"}` — остальные 4 поля не трогаются.

**5. Опиши, как работает OAuth2 простыми словами.**

> OAuth2 — это фреймворк, который позволяет одному приложению получить ограниченный доступ к данным пользователя в другом приложении, не передавая пароль. Сценарий «войти через Яндекс» на сайте X: пользователь жмёт кнопку, X редиректит его на Яндекс, пользователь там логинится и разрешает X доступ, Яндекс возвращает X временный код, X меняет код на access_token, X ходит с этим токеном к API Яндекса за нужными данными. Access_token короткоживущий (минуты-часы), refresh_token долгоживущий (дни-месяцы) и позволяет получать новые access_token'ы без повторной аутентификации пользователя.

**6. Что такое JWT и чем он лучше обычного токена?**

> JWT — это компактный токен в формате header.payload.signature. Header описывает алгоритм подписи, payload содержит утверждения (claims) — кто, с какими правами, до какого времени валиден, signature — подпись сервера над первыми двумя частями. Главное преимущество — самодостаточность: сервер проверяет подпись токена без обращения к БД, что важно для горизонтального масштабирования. Минусы: отозвать выпущенный токен до истечения срока нельзя (только чёрные списки, что убивает преимущество), размер токена растёт с числом claims, токен в утечке — утерян до истечения TTL. Поэтому JWT обычно делают короткоживущим и перевыпускают через refresh_token.

**7. Какие виды пагинации знаешь? Какую выбрал бы для API, отдающего историю платежей абонента?**

> Три основных вида: offset/limit (`?offset=20&limit=10`), page/size (`?page=2&size=10`, по сути то же), cursor-based (`?cursor=...`). Offset прост, но при параллельной записи результат «пляшет» — на третьей странице может попасться строка с первой. Cursor стабилен: сервер выдаёт курсор на следующую страницу, и даже если данные добавились, порядок не ломается. Для истории платежей я бы выбрал cursor-based: платежи идут в хронологическом порядке, добавляются только новые (старые не меняются), и курсор по `payment_id` или `payment_date` даст стабильный результат. Если бы API было для внешнего партнёра и UI был простой — мог бы согласиться на offset ради простоты.

**8. Чем REST отличается от SOAP?**

> SOAP — это протокол с жёстким стандартом: XML-сообщения, WSDL-контракт, встроенная поддержка транзакций, безопасности (WS-Security), идемпотентности. REST — это стиль, более лёгкий, поверх HTTP, обычно с JSON. SOAP тяжелее по байтам и сложнее в реализации, но даёт больше гарантий «из коробки» — поэтому жив в enterprise: банкинг, телеком-биллинг, интеграции с государственными системами. REST — стандарт для современных веб- и мобильных API, где важна скорость разработки и простота потребления. Если бы я интегрировал новый сервис в телеком-биллинг 2010-х годов — скорее всего SOAP; в новых продуктах 2020-х — REST или gRPC.

**9. Что такое GraphQL и когда его выбрать?**

> GraphQL — это язык запросов, где клиент в одном POST-запросе описывает, какие именно поля ему нужны. Сервер возвращает ровно их — не больше, не меньше. Главное преимущество — отсутствие over-fetching (когда REST возвращает 20 полей, а нужно 3) и under-fetching (когда для одного экрана нужно сделать 5 REST-запросов). Минусы: сложнее кэширование (один URL, нельзя использовать HTTP-кэш), сложнее rate limiting (сложно оценить «вес» запроса), риск N+1 на сервере. Я бы выбрал GraphQL для мобильного приложения с разными экранами, где каждый экран хочет своё подмножество полей. Для server-to-server интеграции — REST или gRPC.

**10. Что такое OpenAPI и как BA с ним работает?**

> OpenAPI — это стандарт описания REST API в виде YAML/JSON-файла. Один файл описывает все эндпоинты, методы, параметры, тела запросов/ответов, коды ошибок, схемы аутентификации. На основе файла генерируется интерактивная документация (Swagger UI, Redoc), клиентские SDK, серверные стабы, моки. Для BA OpenAPI — рабочий инструмент: я могу прочитать контракт и понять, какие операции есть, какие поля обязательны, какие статусы возвращаются. И могу написать драфт контракта, оставив разработчикам только уточнить крайние случаи. При изменении API сначала меняем контракт, потом реализацию — это даёт единый источник истины.

**11. Сценарий: опиши API-контракт для «оформление заказа».**

> Заказ — это сущность, у которой есть клиент, набор позиций, способ доставки, способ оплаты, итоговая сумма. Контракт:
>
> `POST /api/v1/orders`
> Заголовки: `Authorization: Bearer <JWT>`, `Content-Type: application/json`, `Idempotency-Key: <uuid>`.
> Тело запроса:
> ```json
> {
>   "items": [{"product_id": "p-123", "quantity": 2}],
>   "delivery": {"type": "courier", "address": "..."},
>   "payment": {"type": "card", "card_token": "tok_abc"}
> }
> ```
> Ответ 201 Created:
> ```json
> {"order_id": "o-456", "status": "created",
>  "total": 1500, "created_at": "2025-08-13T10:00:00Z",
>  "links": {"self": "/orders/o-456", "cancel": "/orders/o-456/cancel"}}
> ```
> Коды ошибок: 400 (невалидное тело), 401 (нет токена), 403 (нет прав), 409 (конфликт, например, товар уже распродан), 422 (тело синтаксически валидно, но семантически неверно — нет такого product_id), 429 (превышен rate limit). Idempotency-Key защищает от задвоения заказа при retry. В ответе 201 — `Location: /orders/o-456` по стандарту.

**12. Что такое rate limiting и как он связан с архитектурой API-шлюза?**

> Rate limiting — ограничение числа запросов от клиента в единицу времени. Защищает сервис от перегрузки и злоупотреблений, обеспечивает честное разделение ресурсов между клиентами. Реализуется обычно на API gateway (Kong, NGINX, Apigee) до того, как запрос дойдёт до бизнес-логики. Заголовки ответа: `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`. При превышении — 429 Too Many Requests с опциональным `Retry-After`. В микросервисной архитектуре gateway ставит лимит глобально на клиента, а внутри — у каждого сервиса может быть свой лимит, чтобы защититься от соседей по сети. Для BA важно понимать, что rate limit — это часть контракта: если мы обещаем партнёру 100 RPS, это должно быть зафиксировано и контролируемо.

### 4. Типичные ошибки и на что смотрят интервьюеры

**Частые ошибки кандидатов:**

- Путают 401 и 403.
- Называют POST идемпотентным или считают, что GET может иметь тело.
- Не понимают, что statelessness — это про сервер, а не про клиента.
- Не могут объяснить разницу между аутентификацией и авторизацией.
- На вопрос «опиши API для X» сразу начинают перечислять URL, не спросив «какие операции нужны бизнесу».
- Забывают про коды ошибок — описывают только happy path.
- Считают, что REST — это стандарт. Это стиль, и «настоящих REST API» в индустрии почти нет (HATEOAS игнорируется почти всеми).

**Сильный vs слабый ответ:**

| Что спрашивают | Слабый ответ | Сильный ответ |
|---|---|---|
| Чем REST отличается от SOAP? | «REST на JSON, SOAP на XML». | Добавляет: SOAP — протокол с жёстким контрактом WSDL и встроенной поддержкой транзакций/безопасности; REST — стиль. SOAP живёт в enterprise (банки, телеком-биллинг), REST — стандарт для новых API. |
| Что такое идемпотентность? | «Повтор не меняет результат». | Называет идемпотентные методы, объясняет, почему для POST идемпототен-ключ спасает при retry, и приводит пример из биллинга. |
| Опиши API для заказа | Сразу пишет POST /createOrder. | Сначала определяет ресурсы и операции, потом для каждой — метод, путь, тело, статусы, включая ошибки и idempotency. |

**На что смотрит интервьюер:**

- Различает ли кандидат аутентификацию и авторизацию (часто путают даже senior'ы).
- Умеет ли проектировать контракт целиком, а не только happy path.
- Понимает ли, что выбор стиля (REST/SOAP/GraphQL) зависит от задачи, а не от моды.
- Знает ли про Idempotency-Key и почему он критичен для платёжных операций.

> **Телеком-акцент:** в телекоме API часто разделены на BSS (Business Support Systems — биллинг, CRM, каталог продуктов) и OSS (Operations Support Systems — инвентарь сети, управление инцидентами). Интеграции между ними — часто SOAP (легаси) или REST (новое). Спроси про специфику: например, API активации услуги на абоненте обычно требует синхронного ответа, а API выгрузки CDR — асинхронного с пагинацией.

## Тема 3. Apache Kafka, gRPC, RabbitMQ

### 1. Теория

#### 1.1. Зачем вообще брокеры и асинхронный обмен

В монолите два модуля вызывают друг друга прямо — синхронно, через функцию или процедуру. В распределённой системе так делать становится опасно: если один сервис упал, другой ждёт и тоже падает. Решение — разорвать связь через посредника:producer кладёт сообщение в брокер, consumer забирает его позже. Это даёт три важных свойства: развязку во времени (producer не обязан ждать consumer), устойчивость к сбоям (сообщение не теряется при падении consumer'а) и масштабируемость (можно добавить consumer'ов).

В телекоме классические сценарии: биллинг отправляет событие «абонент оплатил» — CRM, OSS, маркетинговая платформа забирают каждый своё; биллинг не знает и не должен знать, кто там ещё слушает.

#### 1.2. Apache Kafka — что это и зачем

Kafka — распределённая платформа потоковой обработки (event streaming platform). Формально это не «брокер сообщений» в классическом смысле, а распределённый лог (distributed log): сообщения пишутся в упорядоченный лог и хранятся там дни, недели, месяцы — пока не истечёт retention. Consumer'ы читают лог с любого места и могут перематывать назад (replay).

Ключевые концепции Kafka:

- **Producer** — тот, кто пишет сообщения в Kafka.
- **Consumer** — тот, кто читает.
- **Topic (топик)** — логический канал, в который пишутся сообщения. Аналог «темы» в почтовом списке.
- **Partition (партиция)** — физическое разбиение топика. Каждая партиция — упорядоченный лог. Партиции позволяют параллелить чтение и запись. Внутри одной партиции порядок сообщений гарантирован, между партициями — нет.
- **Offset (офсет)** — позиция consumer'а в партиции. Consumer коммитит офсет — Kafka запоминает, что это сообщение обработано.
- **Consumer group (группа потребителей)** — набор consumer'ов, которые вместе читают топик. Каждая партиция читается ровно одним consumer'ом из группы. Это даёт горизонтальное масштабирование.
- **Broker (брокер)** — сервер Kafka. Кластер состоит из нескольких брокеров.
- **Replication (репликация)** — каждая партиция реплицируется на N брокеров. Один — leader, остальные — followers. Если leader падает, follower становится новым leader'ом.

Главные сценарии Kafka: потоковая обработка событий (streaming), интеграция множества систем через «поток истины» (event backbone), сбор логов и метрик, replay-сценарии (когда нужно перечитать историю заново — например, при запуске нового consumer'а).

#### 1.3. RabbitMQ — классический брокер очередей

RabbitMQ — брокер сообщений, реализующий протокол AMQP. В отличие от Kafka, ориентирован на доставку конкретного сообщения конкретному consumer'у: сообщение удаляется из очереди после ack.

Ключевые концепции RabbitMQ:

- **Producer** — отправитель.
- **Queue (очередь)** — FIFO-буфер сообщений.
- **Consumer** — получатель.
- **Exchange (обменник)** — точка маршрутизации: producer отправляет сообщение в exchange, а не напрямую в очередь. Exchange решает, в какие очереди его положить.
- **Binding (связка)** — правило, связывающее exchange с очередью.
- **Routing key (ключ маршрутизации)** — строка, по которой exchange принимает решение о маршрутизации.

Типы exchange:

- **Direct** — сообщение идёт в очередь, у которой binding key точно равен routing key.
- **Topic** — то же, но с шаблонами (`user.*.created`).
- **Fanout** — сообщение идёт во все очереди, привязанные к exchange (broadcast).
- **Headers** — маршрутизация по заголовкам сообщения.

RabbitMQ гарантирует доставку через механизм ack: consumer подтверждает обработку, и только тогда сообщение удаляется. Если consumer упал без ack — сообщение возвращается в очередь.

#### 1.4. gRPC — синхронный RPC через protobuf

gRPC — фреймворк удалённого вызова процедур (RPC) от Google. Использует HTTP/2 как транспорт и Protocol Buffers (protobuf) как формат сериализации. В отличие от REST, где контракт описывается в OpenAPI, в gRPC контракт — это `.proto`-файл, из которого генерируется код клиента и сервера на разных языках.

Преимущества gRPC:

- **Скорость:** бинарный protobuf компактнее и быстрее JSON.
- **Типизация:** контракт строго типизирован, ошибки ловятся на этапе компиляции.
- **HTTP/2:** мультиплексирование потоков, бинарный фрейминг, меньшая задержка.
- **Streaming:** поддержка потоков в обе стороны (server-streaming, client-streaming, bidirectional).
- **Codegen:** клиентский и серверный код генерируется из `.proto`.

Минусы gRPC:

- **Тяжелее для браузера:** gRPC-Web требует прокси.
- **Менее человекочитаемый:** protobuf — бинарный формат, в отличие от JSON.
- **Требует schema-first подхода:** нельзя «просто вызвать без контракта».

Типичные сценарии gRPC: синхронные вызовы между микросервисами внутри одного ДЦ, где важны задержка и типобезопасность; потоковая передача данных между сервисами.

#### 1.5. Когда что использовать

| Свойство | Kafka | RabbitMQ | gRPC |
|---|---|---|---|
| Паттерн | Event streaming (лог) | Task queue (очередь задач) | RPC (вызов процедуры) |
| Доставка | Pull, с хранением | Push, с удалением после ack | Синхронный вызов |
| Хранение сообщений | Дни/недели/месяцы | До ack consumer'а | Не хранит |
| Replay | Да | Нет (после ack) | Нет |
| Упорядоченность | Внутри партиции | Внутри очереди | Нет (синхронно) |
| Throughput | Очень высокий (миллионы/сек) | Высокий (десятки тысяч/сек) | Зависит от сервиса |
| Latency | Миллисекунды | Миллисекунды | Микросекунды |
| Типичный сценарий | Поток событий, интеграция систем, event sourcing | Разовая задача, routing, deferred jobs | Синхронный вызов сервиса |

Практическое правило:

- Нужен поток событий, который читают несколько систем, и важна возможность перечитать историю? **Kafka**.
- Нужно поставить задачу в очередь и гарантировать её однократную обработку? **RabbitMQ**.
- Нужен синхронный ответ от другого сервиса с малой задержкой? **gRPC** (или REST).

#### 1.6. Семантики доставки

- **At-most-once (не более одного раза):** сообщение может потеряться, но не дойдёт дважды. Реализуется отправкой без подтверждения. Подходит для телеметрии, где потеря пары точек не критична.
- **At-least-once (хотя бы один раз):** сообщение точно дойдёт, но может дойти дважды. Реализуется ack с retry. Самый частый режим. Требует идемпотентности consumer'а — иначе дубли причинят боль.
- **Exactly-once (ровно один раз):** сообщение дойдёт ровно один раз. Реально реализуется только в рамках одной системы (например, внутри Kafka через transactional API). Между гетерогенными системами — почти миф, требуется идемпотентность на стороне consumer'а плюс distributed transaction или outbox pattern.

На интервью часто спрашивают: «у нас at-least-once и consumer задваивает обработку — что делать?» Ответ: сделать consumer идемпотентным через уникальный идентификатор сообщения (message_id) и хранение обработанных ID в БД с уникальным ограничением.

#### 1.7. Гарантии порядка

- **Kafka:** порядок сохраняется внутри одной партиции. Если нужно сохранить порядок событий одного абонента — все его события должны идти в одну партицию. Это делается через ключ партицирования (например, `subscriber_id`): Kafka гарантирует, что все сообщения с одним ключом попадут в одну партицию.
- **RabbitMQ:** порядок сохраняется внутри одной очереди, если один consumer. С несколькими consumer'ами в очереди — порядок не гарантируется (сообщения забираются параллельно).
- **gRPC:** порядок — по умолчанию не гарантирован для независимых вызовов; для streaming — сохраняется.

#### 1.8. Outbox pattern

Outbox pattern — способ гарантировать, что событие «успешная транзакция в БД» и «сообщение в брокер» произойдут атомарно. Идея: в той же транзакции, где меняешь данные, пишешь запись в outbox-таблицу. Отдельный процесс (publisher) читает outbox и отправляет в Kafka/RabbitMQ. Если отправка прошла успешно — помечает запись как отправленную. Это решает классическую проблему «сохранили в БД, но не успели отправить в брокер» (или наоборот).

### 3. Практика

**1. В чём принципиальное отличие Kafka от RabbitMQ?**

> Главное отличие — в модели хранения. Kafka — это распределённый лог: сообщения пишутся в партиции и хранятся там дни или недели, даже после того как consumer их прочитал. Consumer'ы читают с любого офсета и могут перематывать назад (replay). RabbitMQ — это классический брокер очередей: сообщение удаляется из очереди после подтверждения consumer'а. Поэтому Kafka подходит для потоковой обработки и интеграции множества систем через единый поток истины с возможностью перечитать историю, а RabbitMQ — для разовых задач: поставить в очередь, обработать, удалить. Kafka даёт высокий throughput (миллионы сообщений в секунду) и горизонтальное масштабирование через партиции; RabbitMQ — более гибкую маршрутизацию (exchange + routing key).

**2. Объясни, что такое партиция и зачем она нужна.**

> Партиция — это физическое разбиение топика Kafka. Каждая партиция — упорядоченный лог сообщений. Партиции дают две вещи: параллелизм и масштабируемость. Запись в разные партиции идёт параллельно — throughput растёт. Чтение — тоже: каждая партиция читается одним consumer'ом из группы, и добавление consumer'ов в группу ускоряет обработку. Внутри одной партиции порядок сообщений гарантирован, между партициями — нет. Поэтому если мне нужно сохранить порядок событий одного абонента — я задаю ключ партицирования `subscriber_id`, и Kafka гарантированно положит все его сообщения в одну партицию.

**3. Что такое consumer group и как она работает?**

> Consumer group — это набор consumer'ов, совместно читающих топик. Главное правило: каждая партиция читается ровно одним consumer'ом из группы. Если в группе 3 consumer'а и в топике 6 партиций — каждый получит по 2 партиции. Если 7 consumer'ов — один будет простаивать (партиций меньше, чем consumer'ов). Если один consumer упал — Kafka перераспределит его партиции на остальных (rebalance). Это даёт горизонтальное масштабирование: добавил consumer'ов — вырос throughput. Несколько разных consumer group могут читать один топик независимо — у каждой свой набор офсетов.

**4. Объясни разницу между at-least-once и exactly-once. Какую выбрал бы для платёжных событий?**

> At-least-once — сообщение дойдёт хотя бы один раз, возможно дважды. Реализуется ack с retry. Exactly-once — сообщение дойдёт ровно один раз. В рамках одного брокера (Kafka transactional API) — реально. Между гетерогенными системами (Kafka → внешний сервис) — почти миф, требует идемпотентности на стороне consumer'а плюс распределённой транзакции или outbox pattern. Для платёжных событий я бы выбрал at-least-once с идемпотентным consumer'ом: каждое событие имеет уникальный `event_id`, и при обработке consumer проверяет в БД, не обрабатывалось ли уже это событие. Если да — просто ack без повторной обработки. Это надёжнее, чем пытаться реализовать exactly-once на нескольких системах.

**5. Что такое outbox pattern и зачем он нужен?**

> Outbox pattern решает классическую проблему: «сохранили изменение в БД, но не успели отправить событие в брокер» (или наоборот — отправили, но БД упала). Идея: в той же транзакции, где меняем данные, пишем запись в outbox-таблицу. Отдельный publisher-процесс читает outbox и отправляет в Kafka/RabbitMQ. Если отправка прошла успешно — помечает запись как отправленную. Атомарность гарантируется БД-транзакцией: либо изменение и outbox-запись зафиксированы вместе, либо ничего. Это надёжнее, чем «сначала коммит, потом send» — между ними может произойти сбой.

**6. Когда ты выбрал бы gRPC, а когда REST?**

> gRPC я выбрал бы для синхронных вызовов между микросервисами внутри одного ДЦ, где важны задержка, типобезопасность и бинарная эффективность. Контракт в `.proto`-файле, кодген для клиента и сервера — меньше рутины, меньше ошибок рассинхрона. REST — для внешних API, где клиент — браузер или стороннее приложение: REST проще тестировать (curl, Postman), проще кэшировать (HTTP-кэш), привычнее для разработчиков. В телекоме типичная связка: внешние API — REST/OpenAPI, внутренние коммуникации — gRPC, поток событий между сервисами — Kafka.

**7. Сценарий: нужно интегрировать биллинг и CRM. Биллинг сообщает об оплате, CRM обновляет профиль абонента. Что выберешь — Kafka, RabbitMQ или gRPC?**

> Зависит от требований, но я бы начал с Kafka. Причины: биллинг — источник множества событий, и скорее всего рано или поздно захотят слушать те же события ещё маркетинг, fraud, дата-платформа. Kafka позволит добавить consumer'ов без изменения биллинга. События можно перечитать (replay) — если CRM долго не работала, она догонит историю. Плюс у нас будет единый лог «все платежи за всё время», который пригодится для аналитики. RabbitMQ я бы выбрал, если бы была сложная маршрутизация событий по типам — например, разные события в разные очереди с разной обработкой. gRPC — если бы CRM должен был синхронно ответить биллингу «да, я обработал» за миллисекунды, но в описанном сценарии этого не требуется.

**8. Что произойдёт, если consumer в Kafka упадёт и поднимется через час?**

> Ничего страшного — это ключевая фича Kafka. Сообщения не теряются, они хранятся в партициях. Consumer при подъёме прочитает свой последний закоммиченный офсет и продолжит с него. Все сообщения, накопленные за час простоя, будут обработаны. Если consumer был частью группы, во время его падения произошёл rebalance — его партиции временно читали другие consumer'ы. Когда он вернулся — ещё один rebalance, партиции перераспределились. Главное ограничение: если простой дольше retention-периода топика (например, 7 дней) — старые сообщения уже удалены, и consumer их не получит.

**9. В RabbitMQ сообщение удаляется после ack. Что будет, если consumer обработал сообщение, но упал до ack?**

> Сообщение вернётся в очередь и будет передано другому consumer'у. Это базовая гарантия RabbitMQ. Минус — сообщение обработается дважды: первый consumer уже что-то сделал (например, записал в БД), но ack не успел отправить. Поэтому consumer должен быть идемпотентным. Если он просто пишет результат в БД по уникальному message_id с уникальным ограничением — повторная обработка просто завершится ошибкой дублирующего ключа, и consumer спокойно сделает ack. Если же consumer делает что-то с побочными эффектами (отправляет SMS, списывает деньги) — нужно заботиться об идемпотентности на уровне бизнес-логики.

**10. Чем protobuf лучше JSON для межсервисного взаимодействия?**

> Три главных преимущества. Первое — размер: protobuf бинарный, JSON — текстовый. Для больших сообщений разница может быть в 2-5 раз. Второе — скорость: парсинг protobuf быстрее парсинга JSON, и это критично для высоконагруженных RPC. Третье — типизация: protobuf-схема строго типизирована, и код клиента/сервера генерируется из неё. Если обе стороны обновились на новую версию схемы — ошибки ловятся на этапе компиляции, а не в рантайме. Минусы: protobuf не человекочитаемый (нельзя посмотреть в curl), требует schema-first подхода (нельзя «просто вызвать без контракта»), и не работает «из коробки» в браузере — нужен gRPC-Web с прокси.

**11. Что такое rebalance и почему это проблема?**

> Rebalance в Kafka — перераспределение партиций между consumer'ами в группе. Происходит, когда consumer добавляется, удаляется или падает. Во время rebalance чтение приостанавливается: старые партиции отзываются, новые назначаются. Если rebalance идёт долго (например, consumer делает heavy init) — топик «застревает», растёт лаг. Это известная проблема Kafka consumer groups, и в больших кластерах её решают через static group membership (consumer'ы получают стабильные идентификаторы и при кратковременных падениях не вызывают rebalance) и через уменьшение времени session timeout.

**12. У нас at-least-once доставка и consumer иногда обрабатывает сообщение дважды. Что делать?**

> Стандартный рецепт — сделать consumer идемпотентным. Каждое сообщение должно нести уникальный идентификатор (`event_id` или `message_id`). Consumer при обработке проверяет в БД, не обрабатывал ли он уже это сообщение — например, через таблицу `processed_events` с уникальным ограничением на `event_id`. Если дубликат — просто ack без обработки. Альтернатива — логическая идемпотентность на уровне бизнес-операции: «добавить 100 ₽ на баланс по операции X» — операция должна быть не «прибавить 100», а «установить баланс в значение, вычисленное из X». Первый подход проще в реализации, второй — более чистый.

### 4. Типичные ошибки и на что смотрят интервьюеры

**Частые ошибки кандидатов:**

- Считают Kafka и RabbitMQ взаимозаменяемыми — это разные инструменты под разные задачи.
- Думают, что exactly-once «просто работает» — на самом деле требует идемпотентности consumer'а.
- Не понимают, что порядок сообщений в Kafka сохраняется только внутри партиции, а не во всём топике.
- На сценарий «какой инструмент выбрать» отвечают одним словом, не разбирая trade-off'ов.
- Не знают про outbox pattern — классический пробел в знаниях.
- Считают, что gRPC «просто быстрее REST» — забывают про типизацию, codegen, streaming.

**Сильный vs слабый ответ:**

| Что спрашивают | Слабый ответ | Сильный ответ |
|---|---|---|
| Kafka vs RabbitMQ | «Kafka для больших данных, RabbitMQ для очередей». | Объясняет модель хранения (лог vs очередь), replay,Retention, throughput, идемпотентность. |
| Какой инструмент для интеграции биллинга и CRM? | «Kafka, потому что модно». | Разбирает сценарий: множественные consumer'ы в будущем, replay, единый лог → Kafka. Если бы была сложная маршрутизация — RabbitMQ. |
| Что такое exactly-once? | «Сообщение дойдёт один раз». | Объясняет, что в гетерогенных системах это почти миф, и что реальный путь — at-least-once + идемпотентный consumer. |

**На что смотрит интервьюер:**

- Понимает ли кандидат принципиальную разницу между логом (Kafka) и очередью (RabbitMQ).
- Знает ли про семантики доставки и про идемпотентность consumer'а как практический путь.
- Умеет ли аргументировать выбор инструмента под сценарий, а не «потому что Kafka модная».
- Знает ли про outbox pattern — это маркер зрелого разработчика/BA.

> **Телеком-акцент:** в телекоме Kafka часто используют как event backbone: биллинг как источник событий «платеж», «активация услуги», «блокировка», а CRM, OSS, маркетинг, fraud — как consumer'ы. Если доведётся рассказывать про свой опыт — упомяни, что понимаете цикл «событие в биллинге → Kafka → несколько consumer'ов» целиком. RabbitMQ чаще встречается в задачах типа «отправить SMS-уведомление», «обработать заявку в OSS» — там, где нужна разовая задача с гарантированной доставкой.

## Тема 4. Микросервисная архитектура

### 1. Теория

#### 1.1. Монолит vs микросервисы

**Монолит** — приложение, в котором все модули (UI, бизнес-логика, доступ к данным) упакованы в один процесс и разворачиваются вместе. Просто разрабатывать, тестировать, деплоить; тривиально вызывать функции между модулями. Минусы: при росте кодовой базы — длинные релизы, сложно параллельно работать командам, невозможно масштабировать только одну часть (масштабируем весь монолит целиком).

**Микросервисы** — приложение разбито на небольшие сервисы, каждый со своей ответственностью, своей БД и своим циклом релиза. Сервисы общаются по сети (REST/gRPC/Kafka). Плюсы: независимые релизы, независимое масштабирование, технологическая гетерогенность. Минусы: сложность распределённой системы — сетевые сбои, eventual consistency, сложный дебаг, необходимость DevOps-культуры.

Главный вывод: микросервисы — это не «лучше монолита», это компромисс. Их имеет смысл вводить, когда монолит стал слишком большим для одной команды, когда разные части системы имеют разные требования к нагрузке и циклу релиза. Если у вас команда из 5 человек и продукт — MVP, делайте монолит.

#### 1.2. Bounded context (DDD)

Bounded context (ограниченный контекст) — центральная концепция Domain-Driven Design (DDD). Идея: каждая предметная область в бизнесе имеет свои границы, в которых термины означают одно и то же. «Абонент» в биллинге — это плательщик с балансом. «Абонент» в CRM — это контакт с историей обращений. «Абонент» в OSS — это услуга на порту оборудования. Это три разных bounded context'а, и модель «абонента» в каждом своя.

Микросервисы строятся по границам bounded context'ов: один сервис — один контекст. Это даёт чёткие границы ответственности и позволяет командам развивать свои части независимо. BA должен уметь выделять bounded context'ы из бизнес-процессов — это базовый навык для работы в микросервисном проекте.

#### 1.3. Database-per-service

Принцип: каждый микросервис владеет своей БД и не лезет в БД другого сервиса. Доступ к данным другого сервиса — только через его API. Это даёт:

- Слабую связность: можно менять схему БД сервиса, не ломая соседей.
- Независимое масштабирование: тяжёлый сервис может быть на PostgreSQL, лёгкий — на Redis.
- Автономность команд.

Минусы: нет единой картины данных, нет JOIN'ов между сервисами, согласованные транзакции превращаются в проблему (см. Saga).

В телекоме типичный пример: биллинг, CRM, OSS — каждый со своей БД. Если CRM нужно знать баланс абонента — он идёт в API биллинга, а не в его таблицы.

#### 1.4. API Gateway

API Gateway — единая точка входа для внешних клиентов в микросервисную систему. Клиент обращается к gateway, тот маршрутизирует запрос в нужный сервис (или несколько), агрегирует результат, возвращает клиенту.

Функции gateway:

- Маршрутизация запросов.
- Аутентификация и авторизация (централизованно, не в каждом сервисе).
- Rate limiting.
- Логирование и метрики.
- Преобразование протоколов (например, внешний REST → внутренний gRPC).
- Агрегация: один запрос клиента → несколько запросов к сервисам.
- Кэширование.

Популярные реализации: Kong, NGINX, Apigee, AWS API Gateway, Envoy. В российских enterprise используется Kong и собственные решения на базе NGINX.

#### 1.5. Service discovery

В микросервисной системе сервисы постоянно появляются, исчезают, меняют адреса (например, при автомасштабировании). Жёстко прописать адреса в конфигах — не работает. Service discovery — механизм, позволяющий сервисам находить друг друга динамически.

Два подхода:

- **Client-side discovery:** клиент сам спрашивает у service registry (например, Eureka, Consul), где сейчас живёт нужный сервис, и делает запрос напрямую.
- **Server-side discovery:** клиент идёт к балансировщику/load balancer'у, тот сам знает, куда перенаправить (AWS ALB, Kubernetes Service, Envoy).

В Kubernetes service discovery встроен: сервис резолвится по DNS-имени, kube-proxy балансирует.

#### 1.6. Circuit breaker

Circuit breaker (автоматический выключатель) — паттерн защиты от каскадных сбоев. Идея: если вызов сервиса B падает N раз подряд — перестать его вызывать на некоторое время (открыть цепь), быстро возвращая ошибку вместо долгого ожидания. После тайм-аута — попробовать снова (half-open), и если успех — закрыть цепь обратно.

Состояния:

- **Closed:** всё нормально, запросы идут.
- **Open:** ошибок много, запросы отклоняются сразу.
- **Half-open:** пробный запрос, чтобы проверить, восстановился ли сервис.

Без circuit breaker'а каскадный сбой одного сервиса положит всю систему: сервис A ждёт B, B умер, A копит соединения, A тоже умирает, потом C, который ждёт A, и так далее.

Популярные реализации: Resilience4j, Hystrix (deprecated), Polly (.NET).

#### 1.7. Saga pattern

В монолите транзакция охватывает несколько таблиц одной БД — ACID даёт нам атомарность. В микросервисах у каждого сервиса своя БД — распределённой транзакции нет (точнее, есть 2PC, но она не масштабируется и почти не используется). Saga — паттерн для реализации распределённой транзакции через последовательность локальных транзакций с компенсацией.

Каждый шаг саги — локальная транзакция в одном сервисе. Если какой-то шаг падает — выполняются компенсирующие транзакции для уже сделанных шагов, откатывая их эффект.

Два способа координации:

- **Choreography (хореография):** нет центрального координатора. Каждый сервис после выполнения своего шага публикует событие, другие сервисы слушают и делают свой шаг. Децентрализованно, но при росте числа шагов сложно отследить всю сагу.
- **Orchestration (оркестрация):** есть центральный оркестратор, который вызывает сервисы по очереди и сам решает, какие компенсации запустить. Централизованно, проще отладка, но оркестратор — единая точка отказа.

Пример: оформление заказа в e-commerce. Создать заказ → списать сумму с клиента → зарезервировать товар на складе → отправить уведомление. Если «зарезервировать товар» упало — откатываем списание (возвращаем деньги), откатываем создание заказа (статус «отменён»).

#### 1.8. Eventual consistency vs strong consistency

- **Strong consistency (сильная согласованность):** после записи читающий всегда видит новое значение. Реализуется через синхронные транзакции. Простой ценой задержки и доступности (CAP-теорема).
- **Eventual consistency (событийная согласованность):** после записи читающий может временно видеть старое значение, но в конце концов все реплики сходятся. Реализуется через асинхронную репликацию, событийные потоки. Высокая доступность и скорость ценой временной несогласованности.

В микросервисах eventual consistency — норма, потому что данные распределены. Если CRM обновил профиль абонента, биллинг увидит это не мгновенно, а через миллисекунды-секунды (через Kafka-событие). Бизнес должен это понимать: «профиль обновлён» в CRM не значит «применён в биллинге».

#### 1.9. Роль BA в микросервисном проекте

В монолите BA пишет требования к фиче, и разработчики реализуют её в едином коде. В микросервисах BA дополнительно:

1. **Определяет границы сервисов:** какой bounded context за какую бизнес-функцию отвечает.
2. **Описывает контракты между сервисами:** какой сервис вызывает какой, какие данные передаются, какие события публикуются.
3. **Согласует саги:** какие шаги, какие компенсации, кто оркестратор.
4. **Управляет ожиданиями по consistency:** объясняет бизнесу, что «немедленно» в распределённой системе — это «в течение нескольких секунд».
5. **Работает с событиями как с first-class сущностями:** описывает события в каталоге событий и версионизирует их.

Контракты в микросервисном проекте — это не API-эндпоинты одного сервиса, а вся сеть взаимодействий: какие сервисы, какие события протекают, какие саги выполняются. Для описания этого используются C4-диаграммы (Container, Component), sequence-диаграммы, диаграммы саг.

### 3. Практика

**1. В чём главные преимущества и недостатки микросервисов по сравнению с монолитом?**

> Преимущества: независимые релизы (команда сервиса может деплоить 10 раз в день без согласования), независимое масштабирование (тяжёлый сервис масштабируем, лёгкий не трогаем), технологическая гетерогенность (каждый сервис на своём стеке), изоляция ошибок (упал один сервис — другие работают). Недостатки: сложность распределённой системы — сетевые сбои, отладка через несколько сервисов, eventual consistency вместо ACID; необходимость DevOps-культуры (CI/CD, мониторинг, observability); сложность управления контрактами; дублирование инфраструктуры в каждом сервисе. Главный вывод: микросервисы — это не «лучше», это компромисс. Их имеет смысл вводить, когда монолит стал слишком большим для одной команды или когда разные части имеют разные циклы релиза и нагрузки. Если у вас команда из 5 человек и MVP — делайте монолит.

**2. Что такое bounded context и зачем он нужен?**

> Bounded context — центральная концепция DDD. Идея: в каждой предметной области есть своя граница, в которой термины означают одно и то же. «Абонент» в биллинге — это плательщик с балансом. «Абонент» в CRM — контакт с историей обращений. «Абонент» в OSS — услуга на порту оборудования. Это три разных контекста, и модель «абонента» в каждом своя. Bounded context нужен, чтобы команды не дрались за «единую модель» и чтобы сервисы имели чёткие границы. Микросервисы строятся по границам контекстов: один сервис — один контекст. Для BA это базовый навык — уметь из бизнес-процессов выделять контексты.

**3. Зачем нужен database-per-service?**

> Принцип database-per-service означает, что каждый сервис владеет своей БД, и другие сервисы получают к ней доступ только через API. Это даёт слабую связность: можно менять схему БД сервиса, не ломая соседей. Независимое масштабирование: тяжёлый сервис может быть на PostgreSQL, лёгкий — на Redis. Автономность команд. Минусы: нет единой картины данных, нет JOIN'ов между сервисами, согласованные транзакции превращаются в проблему (нужна Saga). Но без этого принципа микросервисы превращаются в «распределённый монолит»: формально разные сервисы, но тесно сцеплены через общую БД.

**4. Что делает API Gateway и зачем он нужен?**

> API Gateway — единая точка входа для клиентов в микросервисную систему. Клиент обращается к gateway, тот маршрутизирует запрос в нужный сервис (или несколько), агрегирует результат и возвращает клиенту. Функции: маршрутизация, централизованная аутентификация и авторизация, rate limiting, логирование и метрики, преобразование протоколов (внешний REST → внутренний gRPC), агрегация, кэширование. Без gateway клиенту пришлось бы знать адреса всех сервисов, аутентифицироваться в каждом отдельно, и агрегировать данные на клиенте. С gateway — единая точка, проще клиенту и безопаснее.

**5. Что такое circuit breaker и почему он важен?**

> Circuit breaker — паттерн защиты от каскадных сбоев. Если вызов сервиса B падает N раз подряд — перестаём его вызывать на время (открываем цепь), быстро возвращая ошибку вместо долгого ожидания. После тайм-аута — пробуем снова (half-open), и если успех — закрываем цепь. Без circuit breaker'а каскадный сбой одного сервиса положит всю систему: A ждёт B, B умер, A копит соединения, A тоже умирает, потом C, который ждёт A. Это называется «cascading failure». Circuit breaker разрывает эту цепочку: A быстро понимает, что B недоступен, и не тратит ресурсы на ожидание. Реализации: Resilience4j, Hystrix (deprecated), Polly.

**6. Объясни Saga pattern. Чем хореография отличается от оркестрации?**

> Saga — паттерн для распределённой транзакции через последовательность локальных транзакций с компенсацией. Каждый шаг — локальная транзакция в одном сервисе. Если шаг падает — выполняются компенсирующие транзакции для уже сделанных шагов. Например, оформление заказа: создать заказ → списать сумму → зарезервировать товар → отправить уведомление. Если «зарезервировать товар» упало — откатываем списание (возвращаем деньги), откатываем создание заказа (статус «отменён»). Хореография — нет центрального координатора, каждый сервис публикует событие, другие слушают. Децентрализованно, но при росте числа шагов сложно отследить. Оркестрация — есть центральный оркестратор, который вызывает сервисы по очереди и решает, какие компенсации запустить. Централизованно, проще отладка, но оркестратор — точка отказа. На практике хореография для простых саг (2-3 шага), оркестрация для сложных.

**7. Чем eventual consistency отличается от strong consistency? Когда каждая приемлема?**

> Strong consistency: после записи читающий всегда видит новое значение. Реализуется синхронными транзакциями. Цена — задержка и ограниченная доступность. Eventual consistency: после записи читающий может временно видеть старое, но реплики сходятся. Реализуется асинхронной репликацией и событиями. Цена — временная несогласованность. В микросервисах eventual consistency — норма, потому что данные распределены. Strong consistency нужна там, где рассогласование критично: списание денег, резервирование товара. Eventual consistency допустима там, где временная задержка не критична: профиль пользователя, статистика просмотров, рекомендации. BA должен понимать, для каких бизнес-функций strong vs eventual, и явно фиксировать это в требованиях — иначе разработчики выберут «по умолчанию eventual», а бизнес будет ждать «мгновенно».

**8. Сценарий: разложить процесс «оформление нового абонента» на микросервисы.**

> Я бы выделил bounded context'ы и соответствующие сервисы:
>
> 1. **CRM-сервис** — ведёт карточку абонента (ФИО, контакты, паспорт), отвечает за идентификацию.
> 2. **Catalog-сервис** — каталог тарифов и услуг, их атрибуты и правила.
> 3. **Order-сервис** — оркестрирует оформление заказа, ведёт его статус.
> 4. **Billing-сервис** — создаёт счёт абонента, начальный баланс, применяет тариф.
> 5. **Provisioning-сервис (OSS)** — активирует услуги на сетевом оборудовании.
> 6. **Notification-сервис** — отправляет welcome-SMS/email.
>
> Процесс: Order-сервис как оркестратор саги. Шаг 1: CRM создаёт абонента → событие `subscriber.created`. Шаг 2: Billing создаёт счёт и применяет тариф → `account.activated`. Шаг 3: Provisioning активирует услуги на оборудовании → `service.provisioned`. Шаг 4: Notification отправляет welcome. Если шаг 3 падает (нет свободных портов) — компенсации: Billing откатывает тариф, CRM помечает абонента как «не активирован». Коммуникация — через Kafka (события) и gRPC (синхронные вызовы оркестратора к сервисам).

**9. В чём разница между хореографией и оркестрацией? Что выбрал бы для сложного процесса из 6 шагов?**

> Хореография — децентрализованная: каждый сервис после своего шага публикует событие, другие слушают и делают свой. Нет единой точки отказа, нет единого координатора. Минусы: при росте числа шагов сложно понять всю картину, сложно добавить новый шаг (нужно знать, кто слушает), сложно отслеживать состояние саги. Оркестрация — централизованная: оркестратор вызывает сервисы по очереди, сам решает, какие компенсации запустить. Плюсы: вся логика в одном месте, проще отладка, проще добавить шаг. Минусы: оркестратор — точка отказа (решается репликацией), оркестратор знает про все сервисы (нарушает инкапсуляцию). Для 6-шагового процесса я бы выбрал оркестрацию: хореография для 6 шагов становится нечитаемой, а оркестратор даёт единое место для отладки и мониторинга. Для 2-3 шагов хореография проще и не требует отдельного компонента.

**10. Что такое service discovery и зачем он нужен?**

> Service discovery — механизм, позволяющий сервисам находить друг друга динамически. В микросервисной системе сервисы постоянно появляются, исчезают, меняют адреса (при автомасштабировании, при падении и подъёме). Жёстко прописать адреса в конфигах — не работает. Два подхода: client-side discovery — клиент сам спрашивает у service registry (Eureka, Consul), где сейчас живёт нужный сервис, и делает запрос напрямую. Server-side discovery — клиент идёт к балансировщику, тот сам знает, куда перенаправить (AWS ALB, Kubernetes Service, Envoy). В Kubernetes service discovery встроен: сервис резолвится по DNS-имени, kube-proxy балансирует.

**11. Что такое распределённый монолит и как его избежать?**

> Распределённый монолит — формально микросервисная архитектура, но фактически сервисы тесно сцеплены: изменение одного требует одновременного релиза другого, общая БД, синхронные цепочки вызовов от которых нельзя избавиться, падение одного роняет других. Симптомы: один релиз на все сервисы, общая БД, разработчики боятся менять контракт. Избежать: соблюдать database-per-service, использовать асинхронные события вместо синхронных вызовов где можно, версионировать контракты, делать backward-compatible изменения, выделять bounded context'ы осознанно, а не по командам. Если два сервиса всегда релизятся вместе — это один сервис, и его стоит объединить.

**12. Как BA работает с событиями в микросервисной системе?**

> События в микросервисах — first-class сущности, BA должен работать с ними так же серьёзно, как с API. В моих задачах: описывать события в каталоге (event catalog), версияировать их (поле `event_version`), описывать схему (protobuf/JSON Schema), определять producer'а и consumer'ов, описывать, что происходит при получении события. События должны быть названы в прошедшем времени (`subscriber.created`, `payment.processed`), а не в повелительном (`create_subscriber`) — это маркер зрелости. BA также описывает саги: какие шаги, какие события публикуются, какие компенсации запускаются при сбое. Для всего этого удобно использовать sequence-диаграммы и таблицы событий.

### 4. Типичные ошибки и на что смотрят интервьюеры

**Частые ошибки кандидатов:**

- Считают микросервисы «лучше» монолита по умолчанию — не понимают компромисса.
- Не могут объяснить, что такое bounded context, и путают его с сервисом.
- Думают, что database-per-service — это про «у каждого своя таблица». Нет — это про «у каждого своя БД, и другой не лезет».
- На вопрос про сагу называют только happy path, забывая про компенсации.
- Не различают strong и eventual consistency, не понимают, когда каждая нужна.
- Не понимают, что API Gateway — это не то же самое, что load balancer.
- На сценарии декомпозиции сразу называют «биллинг, CRM, биллинг ещё раз», не выделяя bounded context'ы.

**Сильный vs слабый ответ:**

| Что спрашивают | Слабый ответ | Сильный ответ |
|---|---|---|
| Зачем микросервисы? | «Они лучше масштабируются». | Разбирает trade-off'ы: независимые релизы, масштабирование, технологическая гетерогенность — ценой сложности распределённой системы. Оговаривает, когда микросервисы не нужны. |
| Что такое Saga? | «Это распределённая транзакция». | Объясняет последовательность локальных транзакций с компенсацией, разницу хореографии и оркестрации, приводит пример из телекома. |
| Декомпозиция процесса оформления заказа | Называет «сервис заказов, сервис оплаты, сервис склада». | Сначала выделяет bounded context'ы, потом для каждого — сервис, потом описывает сагу, включая компенсации. |

**На что смотрит интервьюер:**

- Понимает ли кандидат, что микросервисы — компромисс, а не «лучше монолита».
- Умеет ли выделять bounded context'ы из бизнес-процесса.
- Знает ли про саги и компенсации, а не только happy path.
- Различает ли strong и eventual consistency и может ли объяснить бизнесу.
- Умеет ли описывать сеть контрактов между сервисами, а не только один сервис.

> **Телеком-акцент:** в телекоме классический набор микросервисов — BSS (биллинг, CRM, каталог продуктов, order management) и OSS (инвентарь сети, provisioning, fault management). BA в телекоме часто работает на стыке: например, заказ на подключение проходит через Order Management, активирует услуги через Provisioning, создаёт счёт в Billing, отправляет welcome через Notification. Умение описать этот цикл с точки зрения саги и контрактов — сильный сигнал на интервью.

## Тема 5. BPMN, UML, C4 model, ERD

### 1. Теория

#### 1.1. Зачем BA диаграммы

Диаграмма — это не «картинка для красоты», а инструмент коммуникации. BA использует разные типы диаграмм для разных аудиторий и разных задач. Нет «лучшей» диаграммы — есть подходящая под цель. Топ-менеджменту нужна простота, разработчикам — точность, бизнесу — процесс, тестировщикам — последовательность вызовов. На интервью часто проверяют, умеешь ли ты выбрать правильный тип диаграммы под задачу — это маркер зрелости.

#### 1.2. BPMN — Business Process Model and Notation

BPMN — стандарт описания бизнес-процессов от OMG. Цель — единый язык между бизнесом и IT. Версия 2.0 (BPMN 2.0) — текущий стандарт, поддерживается многими инструментами (Camunda, Bizagi, Draw.io, Lucidchart).

Ключевые элементы BPMN:

**Pools и lanes (пулы и дорожки):**

- **Pool** — участник процесса (организация или роль). Один пул = одна организация. Если в процессе участвуют несколько организаций — несколько пулов.
- **Lane** — дорожка внутри пула. Разделение по ролям или подразделениям внутри одной организации. Например, пул «Оператор» с дорожками «Sales», «Биллинг», «Техподдержка».

**События (events):**

- **Start event (стартовое)** — круг с тонкой границей. Точка начала процесса. Бывает: пустой (без триггера), по сообщению (конверт), по времени (часы), по сигналу (треугольник).
- **Intermediate event (промежуточное)** — круг с двойной границей. Что-то происходит в середине процесса. Бывает catching (ловит событие) и throwing (бросает).
- **End event (конечное)** — круг с толстой границей. Точка завершения процесса или ветки. Бывает: пустой, с сообщением (отправлено), с ошибкой (terminate), со спецификацией сообщения.

**Шлюзы / gateways (развилки):**

- **Exclusive (XOR)** — ромб с X внутри. Выбор ровно одной ветки по условию. «Если баланс > 0, продолжаем; иначе — блокировка».
- **Parallel (AND)** — ромб с + внутри. Все ветки выполняются параллельно, обязательны. Ждём завершения всех.
- **Inclusive (OR)** — ромб с O внутри. Выполняется одна или несколько веток по условиям.
- **Event-based** — ромб с шестиугольником внутри. Выбор ветки по тому, какое событие наступит первым.

**Задачи и подпроцессы:**

- **Task (задача)** — прямоугольник со скруглёнными углами. Единичная работа.
- **Subprocess (подпроцесс)** — прямоугольник с + внизу. Сворачивает набор задач в один блок. Сворачиваем, когда процесс слишком большой для одной диаграммы.
- **Call activity** — вызов глобального процесса, определённого отдельно.

**Потоки:**

- **Sequence flow** — сплошная стрелка. Порядок выполнения внутри одного пула.
- **Message flow** — пунктирная стрелка с конвертом. Обмен сообщениями между пулами.
- **Association** — точечная линия. Комментарии и артефакты.

В телекоме классический BPMN-процесс — «Подключение нового абонента»: старт → заявка от клиента → проверка доступности адреса (шлюз XOR: доступно / недоступно) → оформление договора (параллельно: биллинг создаёт счёт, OSS резервирует порт) → активация услуги → отправка welcome → конец.

#### 1.3. UML — Unified Modeling Language

UML — семейство нотаций для описания программных систем. Из 14 типов диаграмм BA на практике использует четыре:

**Use case diagram (диаграмма прецедентов):**

- Показывает: какие акторы взаимодействуют с системой, какие сценарии (use cases) существуют.
- Аудитория: заказчики, бизнес-аналитики, продакт-менеджеры.
- Когда использовать: в начале проекта, для определения границ системы и сценариев.
- Элементы: актор (человечек), use case (эллипс), системная граница (прямоугольник), ассоциации (линии), `<<include>>` и `<<extend>>` (зависимости).

**Sequence diagram (диаграмма последовательности):**

- Показывает: какие сообщения и в каком порядке передаются между объектами во времени.
- Аудитория: разработчики, тестировщики.
- Когда использовать: для описания конкретного сценария в виде обмена сообщениями между сервисами/компонентами.
- Элементы: lifeline (вертикальная линия участника), сообщения (стрелки), activation bar (прямоугольник активности), alt/opt/loop (фреймы для условий и циклов).

**Activity diagram (диаграмма деятельности):**

- Показывает: поток работ (workflow) в системе. Похоже на BPMN, но фокус на системе, а не на бизнес-процессе.
- Аудитория: разработчики, тестировщики.
- Когда использовать: для описания алгоритма или workflow внутри системы.
- Элементы: начальный/конечный узел, action (закруглённый прямоугольник), decision (ромб), fork/join (толстая линия для параллельности), swimlane (дорожка).

**Class diagram (диаграмма классов):**

- Показывает: структуру системы — классы, их атрибуты, методы и отношения.
- Аудитория: разработчики, архитекторы.
- Когда использовать: для моделирования предметной области (domain model), для проектирования БД.
- Элементы: класс (прямоугольник с тремя секциями: имя, атрибуты, методы), отношения (ассоциация, наследование, агрегация, композиция) с указанием кратности (1, 0..*, 1..*).

#### 1.4. C4 model

C4 model — предложенная Саймоном Брауном методика описания архитектуры через 4 уровня детализации. Идея: как Google Maps — от континента до здания. Каждый уровень раскрывает детали предыдущего.

**Level 1 — Context (контекст системы):**

- Показывает: систему в целом и её внешнее окружение — пользователи и внешние системы, с которыми она взаимодействует.
- Аудитория: топ-менеджмент, заказчики, все заинтересованные.
- Один контейнер = система. Стрелки — зависимости.
- Пример: «Система биллинга оператора» ↔ «Абонент» (через mobile app), ↔ «CRM», ↔ «Банк» (через платёжный шлюз).

**Level 2 — Container (контейнеры):**

- Показывает: внутреннее устройство системы — контейнеры (deployable units): web-app, API, БД, message broker.
- Аудитория: архитекторы, техлиды, разработчики.
- Контейнер — не Docker, а «единица деплоя»: приложение, БД, очередь.
- Пример: «Система биллинга» раскрывается на «Web UI», «Billing API», «БД биллинга», «Kafka».

**Level 3 — Component (компоненты):**

- Показывает: компоненты внутри одного контейнера — модули, классы, подсистемы.
- Аудитория: разработчики конкретного контейнера.
- Пример: «Billing API» раскрывается на «PaymentService», «TariffService», «InvoiceService», «NotificationClient».

**Level 4 — Code (код):**

- Показывает: классы и их отношения (по сути, UML class diagram).
- Аудитория: разработчики конкретного компонента.
- На практике почти не рисуется — autogenerated из кода, и быстро устаревает.

BA чаще всего работает на уровнях 1-3. Level 4 — прерогатива разработчиков.

#### 1.5. ERD — Entity-Relationship Diagram

ERD — диаграмма «сущность-связь», описывает структуру данных: какие сущности, какие у них атрибуты, какие между ними связи и какой кратности.

Ключевые элементы:

- **Entity (сущность)** — прямоугольник. Класс объектов: «Абонент», «Договор», «Платёж».
- **Attribute (атрибут)** — овал или строка в прямоугольнике. Свойство сущности: «имя», «дата рождения». Ключевые атрибуты — первичный ключ (PK), внешний ключ (FK).
- **Relationship (связь)** — линия между сущностями. «Абонент подписан на тариф».
- **Cardinality (кратность)** — сколько экземпляров одной сущности связано с одним экземпляром другой:
  - **1:1** — один к одному (у абонента один активный договор).
  - **1:N** — один ко многим (у абонента много платежей).
  - **N:M** — многие ко многим (абоненты пользуются многими услугами, услуга оказывается многим абонентам). На уровне БД реализуется через ассоциативную таблицу.

**Нотации:**

- **Crow's Foot (воронья лапка):** современный стандарт, кратность обозначается значками на концах линии (| — ровно один, ○ — ноль или больше, < — много, в виде «лапки»). Самая частая нотация в инструментах.
- **Chen (нотация Чена):** связи обозначаются ромбом на линии. Более академичная, реже встречается на практике.
- **IDEF1X:** стандарт министерства обороны США, встречается в enterprise.

В телекоме ERD рисуют для биллинга: «Абонент» (1) → «Договор» (N) → «Услуга» (N:M через «Подписка») → «Тариф» (1:N) → «Платёж» (1:N от абонента).

### 3. Практика

**1. Что такое BPMN и какие у него ключевые элементы?**

> BPMN — Business Process Model and Notation, стандарт OMG для описания бизнес-процессов. Цель — единый язык между бизнесом и IT. Ключевые элементы: пулы (организации) и дорожки (роли внутри организации), события (стартовые, промежуточные, конечные), задачи (единичные работы) и подпроцессы (свёрнутые группы задач), шлюзы (развилки: exclusive — выбор одной ветки, parallel — все ветки, inclusive — несколько), потоки последовательности (сплошная стрелка внутри пула) и потоки сообщений (пунктирная стрелка между пулами). В телекоме типичный BPMN-процесс — «Подключение нового абонента»: старт → заявка → проверка адреса (XOR-шлюз) → параллельно биллинг создаёт счёт, OSS резервирует порт → активация → welcome → конец.

**2. В чём разница между exclusive, parallel и inclusive шлюзами?**

> Exclusive (XOR) — выбор ровно одной ветки по условию. Аналог if-else. «Если баланс > 0, продолжаем; иначе — блокировка». Parallel (AND) — все ветки выполняются параллельно, обязательны. Ждём завершения всех. Аналог — fork/join. Используется, когда несколько независимых работ нужно сделать одновременно: «биллинг создаёт счёт И OSS резервирует порт». Inclusive (OR) — выполняется одна или несколько веток по условиям. Может выполняться одна, две или все. Ждём завершения только тех, что запустились. В телекоме встречается реже, обычно когда часть работ опциональна в зависимости от типа абонента.

**3. Зачем нужны пулы и дорожки в BPMN?**

> Пул — участник процесса, обычно организация. Если в процессе участвуют несколько организаций — несколько пулов с обменом сообщениями через пунктирные стрелки. Например, пул «Оператор» и пул «Банк»: оператор отправляет платёжное поручение, банк отвечает подтверждением. Дорожка (lane) — разделение внутри одного пула по ролям или подразделениям. Пул «Оператор» с дорожками «Отдел продаж», «Биллинг», «Техподдержка». Дорожки показывают, кто выполняет каждую задачу, без необходимости плодить пулы. Если процесс внутри одной организации — один пул с дорожками; если между организациями — несколько пулов.

**4. Какие типы UML-диаграмм ты используешь как BA и в каких случаях?**

> На практике — четыре. Use case diagram — в начале проекта, для определения границ системы и сценариев: какие акторы, какие use cases. Хорошо подходит для общения с заказчиком. Sequence diagram — для описания конкретного сценария как обмена сообщениями между сервисами/компонентами: «абонент инициирует платёж → billing создаёт charge → bank gateway списывает → billing обновляет баланс → notification отправляет SMS». Это для разработчиков и тестировщиков. Activity diagram — для описания workflow внутри системы, похожа на BPMN, но фокус на системе, а не на бизнес-процессе. Class diagram — для моделирования предметной области и проектирования БД: сущности, атрибуты, отношения с кратностью. Остальные 10 типов UML (state, object, deployment и т.д.) на практике BA почти не использует.

**5. Что такое C4 model и какие у неё уровни?**

> C4 model — методика описания архитектуры через 4 уровня детализации, предложенная Саймоном Брауном. Аналог — Google Maps: от континента до здания. Level 1 Context — система в целом и её окружение (пользователи, внешние системы). Для топ-менеджмента и заказчиков. Level 2 Container — внутреннее устройство системы: контейнеры (web-app, API, БД, broker). Для архитекторов и техлидов. Level 3 Component — компоненты внутри одного контейнера: модули, классы. Для разработчиков. Level 4 Code — классы и их отношения, по сути UML class diagram. На практике почти не рисуется, генерируется из кода. BA чаще работает на уровнях 1-3.

**6. Сценарий: нужно показать бизнес-процесс топ-менеджменту. Что выберешь — BPMN, UML activity или C4?**

> BPMN. Топ-менеджменту нужно показать бизнес-процесс: роли, шаги, развилки, точки взаимодействия с внешними системами. BPMN для этого создан — единый язык между бизнесом и IT, понятный и нетехническим людям. UML activity — больше про внутренний workflow системы, его бизнес не поймёт. C4 — про архитектуру, а не про процесс. Если процесс нужно показать в окружении систем — добавлю C4 Context (Level 1) как вводную картинку, а затем BPMN для самого процесса. Это типичная комбинация: контекст системы + бизнес-процесс в нём.

**7. Сценарий: нужно показать взаимодействие сервисов разработчикам. Что выберешь?**

> C4 Container (Level 2) + sequence diagram. C4 Container показывает, какие контейнеры (API, БД, broker) участвуют и как они связаны статически. Sequence — для конкретного сценария: «абонент платит → запрос через API gateway → billing service → Kafka → notification service». Вместе это даёт и статическую картину (что с чем связано), и динамическую (что происходит во времени). Если система сложная — добавлю C4 Component для разбора одного контейнера. BPMN здесь не подходит — он для бизнес-процессов, разработчикам важнее технические контракты.

**8. Что такое ERD и какие у неё нотации?**

> ERD — Entity-Relationship Diagram, диаграмма «сущность-связь» для описания структуры данных. Элементы: сущности (классы объектов — Абонент, Договор), атрибуты (свойства — имя, дата рождения), связи между сущностями с указанием кратности: 1:1, 1:N, N:M. N:M на уровне БД реализуется через ассоциативную таблицу. Нотации: Crow's Foot (воронья лапка) — современный стандарт, кратность значками на концах линии, чаще всего в инструментах; Chen (нотация Чена) — связи обозначаются ромбом, более академичная; IDEF1X — стандарт минобороны США, встречается в enterprise. В телекоме ERD рисую для биллинга: Абонент → Договор → Услуга → Тариф → Платёж, с указанием кратности.

**9. Объясни разницу между агрегацией и композицией в class diagram.**

> Оба — варианты отношения «часть-целое», но с разной силой связи. Агрегация (полый ромб на стороне целого) — слабая связь: часть может существовать без целого. «Отдел состоит из сотрудников» — сотрудник может перейти в другой отдел. Композиция (закрашенный ромб) — сильная связь: часть не существует без целого, жизненный цикл частей совпадает с целым. «Заказ состоит из позиций заказа» — при удалении заказа позиции тоже удаляются. На практике в DDD-моделях агрегаты (aggregate roots) — это композиция, а ссылки между агрегатами — ассоциация или агрегация.

**10. Что такое `<<include>>` и `<<extend>>` в use case diagram?**

> `<<include>>` — обязательное включение одного use case в другой. «Оформить заказ» обязательно `<<include>>` «Авторизоваться». Это всегда вызывается. Используется для выделения общего поведения, повторяющегося в нескольких use case'ах. `<<extend>>` — опциональное расширение. «Оформить заказ» может `<<extend>>` «Применить промокод» — это опциональный сценарий, который выполняется только при определённом условии. Стрелка `<<extend>>` идёт от расширяющего к базовому, `<<include>>` — от базового к включаемому. На практике этими отношениями не стоит злоупотреблять — если их слишком много, диаграмма становится нечитаемой, лучше описать сценарии в тексте.

**11. Сценарий: тебе нужно описать процесс «обработка обращения абонента в техподдержку» для всех stakeholders. Какие диаграммы нарисуешь?**

> Я бы нарисовал три уровня. Первый — BPMN-диаграмма процесса: пулы «Абонент» и «Оператор» с дорожками «Первая линия», «Вторая линия», «Бэк-офис». Старт по обращению → классификация → XOR: решено на 1-й линии / эскалация на 2-ю / эскалация в бэк-офис → параллельно: решение + уведомление абоненту → закрытие обращения. Второй — C4 Container, чтобы показать, какие системы участвуют (CRM, Ticketing, Knowledge Base, Notification) и как они связаны. Третий — sequence diagram для одного сценария: «обращение эскалируется во 2-ю линию» — кто кого вызывает в каком порядке. Три диаграммы дают три уровня понимания: бизнес-процесс (для менеджмента), архитектура (для архитекторов), конкретный сценарий (для разработчиков и QA).

**12. Что общего между BPMN и UML activity и в чём разница?**

> Общее: обе нотации описывают поток работ через задачи, развилки, параллельность. Визуально похожи — прямоугольники, ромбы, стрелки. Разница: BPMN — стандарт для бизнес-процессов, фокус на ролях (пулы, дорожки), обмене сообщениями между организациями, понятен нетехническим стейкхолдерам. UML activity — для внутреннего workflow системы, фокус на логике и состояниях, с фреймами alt/loop для условий и циклов. На практике: если описываешь бизнес-процесс для заказчика — BPMN; если описываешь внутреннюю логику системы для разработчиков — activity. В телекоме оба встречаются: BPMN для «как происходит процесс в компании», activity для «как система обрабатывает обращение шаг за шагом».

### 4. Типичные ошибки и на что смотрят интервьюеры

**Частые ошибки кандидатов:**

- Считают BPMN и UML activity одним и тем же — это разные нотации под разные задачи.
- Не различают include и extend в use case.
- Путают агрегацию и композицию в class diagram.
- Не могут объяснить, зачем C4 нужен 4 уровня — обычно вспоминают только Context.
- На сценарий «какую диаграмму выбрать» отвечают одной нотацией, не разбирая аудиторию.
- Рисуют ERD без указания кратности связей.
- Не знают про дорожки (lanes) в BPMN и лепят все задачи в один пул.

**Сильный vs слабый ответ:**

| Что спрашивают | Слабый ответ | Сильный ответ |
|---|---|---|
| Чем BPMN отличается от UML activity? | «Они похожи». | BPMN — для бизнес-процессов с ролями и пулами, понятен бизнесу. Activity — для внутреннего workflow системы, для разработчиков. |
| Какую диаграмму выбрал бы для топ-менеджмента? | «BPMN, потому что модно». | Сначала уточняет, что показываем: процесс → BPMN; систему в окружении → C4 Context. Чаще всего комбинация. |
| Что такое C4? | «Это 4 уровня». | Называет все 4 (Context, Container, Component, Code), объясняет аудиторию каждого, упоминает, что Level 4 почти не рисуется. |

**На что смотрит интервьюер:**

- Умеет ли выбрать подходящий тип диаграммы под аудиторию и задачу.
- Различает ли бизнес-процесс (BPMN) и системный workflow (activity).
- Знает ли уровни C4 и их назначение.
- Может ли нарисовать ERD с указанием кратности и нотации Crow's Foot.
- Понимает ли разницу между include и extend, агрегацией и композицией.

> **Телеком-акцент:** в телекоме процессы часто сложные и многосторонние — подключение, биллинг, техподдержка, разрешение инцидентов. BA в телекоме регулярно рисует BPMN для описания «как заявка проходит от абонента до активации услуги», C4 Container для «какие системы участвуют», sequence diagram для «что происходит при оплате через мобильное приложение». Умение свободно переключаться между нотациями — обязательный навык. Если доведётся рассказывать про опыт — упомяни, что использовал разные нотации под разные аудитории: BPMN для бизнеса, C4 для архитекторов, sequence для разработчиков.

## Тема 6. UAT (User Acceptance Testing)

### 1. Теория

#### 1.1. Место UAT в SDLC

SDLC (Software Development Life Cycle) — жизненный цикл разработки. Независимо от методологии (Waterfall, Agile, гибрид), в нём есть фазы тестирования, и UAT — последняя перед релизом. UAT (User Acceptance Testing, приёмочное тестирование пользователем) — фаза, на которой реальные пользователи или их представители проверяют, что система решает их бизнес-задачи.

Цепочка тестирования в типичном проекте:

1. **Unit-тестирование** — разработчик проверяет отдельные функции/классы.
2. **Integration-тестирование** — проверка взаимодействия модулей или сервисов.
3. **System-тестирование** — проверка системы целиком, end-to-end, обычно QA-командой.
4. **UAT** — проверка соответствия бизнес-требованиям, пользователем или от его имени.

После UAT — sign-off (формальное одобрение) и релиз.

#### 1.2. Чем UAT отличается от других видов тестирования

| Вид | Кто делает | Что проверяет | Когда |
|---|---|---|---|
| Unit | Разработчик | Корректность отдельных функций | Во время разработки |
| Integration | QA / разработчик | Взаимодействие модулей/сервисов | После unit |
| System | QA | End-to-end сценарии, нефункциональные требования (производительность, безопасность) | После integration |
| Regression | QA | Что новое не сломало старое | Перед каждым релизом |
| UAT | Пользователь / BA от имени пользователя | Соответствие бизнес-требованиям и удобство | После system, перед релизом |

Ключевое отличие UAT — фокус на бизнес-ценности, а не на технической корректности. Если system-тестирование спрашивает «работает ли функция?», UAT спрашивает «решает ли это мою бизнес-задачу и удобно ли мне этим пользоваться?».

#### 1.3. Entry criteria

Условия, при которых можно начинать UAT:

- System-тестирование завершено, критических и серьёзных дефектов нет.
- Все test cases UAT написаны и согласованы с бизнесом.
- Окружение UAT подготовлено и доступно (отдельное от dev/test).
- Тестовые данные подготовлены и anonymизированы (если это прод-подобные данные).
- Документация (user stories, acceptance criteria, user manual) готова.
- Бизнес-пользователи доступны и выделено время на UAT.

Если entry criteria не выполнены — UAT начинать нельзя: будет хаос, дефекты будут заведены не на то, окружение будет падать, бизнес потеряет доверие.

#### 1.4. Exit criteria

Условия, при которых UAT считается завершённым:

- Все test cases выполнены (passed/failed).
- Все critical и high severity дефекты исправлены и перепроверены.
- Medium и low дефекты либо исправлены, либо задокументированы как acceptable для релиза (с согласия бизнеса).
- Sign-off получен от бизнес-заказчика.
- Известны workaround'ы для неприоритетных дефектов.

Sign-off — формальное согласие бизнеса: «мы приняли, можно в прод». Без него релиз не идёт.

#### 1.5. Test case vs test scenario

- **Test scenario (тестовый сценарий)** — высокоуровневое описание: что проверить. «Абонент с положительным балансом может оформить заказ на новую услугу». Один сценарий = одна бизнес-функция.
- **Test case (тест-кейс)** — детальное описание: предусловия, шаги, ожидаемый результат. Один сценарий раскрывается в несколько test cases: «оформление заказа с карты», «оформление заказа со счёта мобильного», «оформление заказа при недостатке средств» и т.д.

Test scenario — для общения с бизнесом и планирования UAT. Test case — для исполнителя, который будет проходить тесты.

#### 1.6. Acceptance criteria

Acceptance criteria (критерии приёмки) — условия, при которых user story считается выполненной. Это главный артефакт, связывающий разработку и UAT: QA пишет test cases на основе acceptance criteria, и UAT проверяет их выполнение.

Формат Given/When/Then (Gherkin, BDD):

```
Given [предусловие]
When [действие]
Then [ожидаемый результат]
```

Пример для user story «Абонент может пополнить баланс с карты»:

```
Given: абонент с активным договором и балансом 100 ₽
When: абонент инициирует пополнение на 500 ₽ с валидной карты
Then: баланс становится 600 ₽, создаётся запись о платеже, отправляется SMS-подтверждение
```

Хорошие acceptance criteria:

- Конкретные и проверяемые (не «работает быстро», а «откликается за < 2 сек»).
- Атомарные (один критерий — одна проверка).
- Покрывают и happy path, и крайние случаи.
- Согласованы с бизнесом до начала разработки.

#### 1.7. Defect severity vs priority

- **Severity (серьёзность)** — техническая оценка, насколько сильно дефект влияет на систему. Бывает: Critical (система не работает), High (ключевая функция не работает), Medium (часть функции не работает, есть workaround), Low (косметика).
- **Priority (приоритет)** — бизнес-оценка, как быстро нужно исправить. Бывает: P1 (немедленно), P2 (в этом релизе), P3 (в следующем релизе), P4 (когда-нибудь).

Severity и priority не всегда совпадают. Опечатка на главной странице банка (Low severity) — P1, потому что падает доверие. Редкий баг в админке (High severity) — P3, потому что есть workaround и мало пользователей.

В UAT важно различать: пользователь репортит дефект — это не значит, что он critical. BA вместе с QA и разработчиком triage'ит (сортирует) дефекты по severity и priority.

#### 1.8. Sign-off process

Sign-off — формальное одобрение бизнесом готовности системы к релизу. Процесс:

1. По завершении UAT BA собирает результаты: сколько test cases passed/failed, какие дефекты открыты, какие закрыты.
2. BA и QA проводят triage: какие дефекты блокируют релиз (critical/high, нет workaround), какие можно отложить.
3. BA презентует результаты бизнес-заказчику, объясняет риски.
4. Бизнес принимает решение: sign-off (да, в прод), conditional sign-off (да, но с условием исправить X в Y-сроке), или no-go (возврат на доработку).
5. Решение фиксируется в документе или тикет-системе.

Conditional sign-off — частый случай: бизнес понимает, что часть дефектов некритична, и готов релизить с известными issues, если они будут исправлены в ближайшем patch.

#### 1.9. Роль BA vs QA в UAT

**BA:**

- Пишет acceptance criteria для user stories.
- Помогает бизнесу формулировать test scenarios.
- Поддерживает тест-кейсы в актуальном состоянии при изменении требований.
- Triage'ит дефекты с точки зрения бизнес-приоритетов.
- Ведёт переговоры между бизнесом и разработкой при спорных дефектах.
- Презентует результаты UAT бизнесу и получает sign-off.

**QA:**

- Пишет детальные test cases на основе acceptance criteria.
- Подготавливает тестовые данные.
- Настраивает окружение UAT.
- Выполняет тесты и репортит дефекты.
- Проводит regression после исправлений.
- Готовит test execution report.

В UAT часто участвуют и реальные пользователи (subject matter experts от бизнеса), особенно в крупных проектах. BA их координирует и помогает.

### 3. Практика

**1. Что такое UAT и какое место он занимает в SDLC?**

> UAT — User Acceptance Testing, приёмочное тестирование пользователем. Это последняя фаза тестирования перед релизом, на которой реальные пользователи или их представители проверяют, что система решает их бизнес-задачи. В типичной цепочке unit → integration → system → UAT → релиз, UAT идёт после system-тестирования. Ключевое отличие UAT от других видов — фокус на бизнес-ценности, а не на технической корректности. System-тестирование спрашивает «работает ли функция?», UAT спрашивает «решает ли это мою бизнес-задачу и удобно ли мне этим пользоваться?». Без UAT и sign-off релиз не идёт.

**2. Чем UAT отличается от functional и regression тестирования?**

> Functional testing проверяет, что система делает то, что написано в требованиях — буквально, по спецификации. Это делает QA. Regression testing проверяет, что новая функциональность не сломала старую — тоже QA. UAT проверяет, что система решает бизнес-задачу пользователя, и удобна в использовании — это делает пользователь или BA от его имени. Functional может пройти, а UAT — нет: например, функция работает по спеке, но пользователь считает её неудобной или не решающей его реальную задачу. В таком случае — это сигнал, что спека была неточной или собрана не от тех людей.

**3. Что такое entry и exit criteria для UAT?**

> Entry criteria — условия для начала UAT: system-тестирование завершено, критических дефектов нет, test cases UAT написаны и согласованы, окружение UAT готово и отделено от dev/test, тестовые данные подготовлены, бизнес-пользователи доступны. Если entry criteria не выполнены — UAT начинать нельзя: будет хаос. Exit criteria — условия завершения: все test cases выполнены, critical и high дефекты исправлены, medium/low либо исправлены, либо задокументированы как acceptable, sign-off получен, workaround'ы известны. Sign-off — формальное согласие бизнеса: «мы приняли, можно в прод».

**4. Чем test case отличается от test scenario?**

> Test scenario — высокоуровневое описание: что проверить. «Абонент с положительным балансом может оформить заказ на новую услугу». Один сценарий = одна бизнес-функция. Test case — детальное описание: предусловия, шаги, ожидаемый результат. Один сценарий раскрывается в несколько test cases: «оформление с карты», «оформление со счёта мобильного», «оформление при недостатке средств». Test scenario — для общения с бизнесом и планирования UAT. Test case — для исполнителя, который будет проходить тесты. На интервью часто ловят на том, что кандидат путает эти понятия.

**5. Что такое acceptance criteria и в каком формате их пишут?**

> Acceptance criteria — условия, при которых user story считается выполненной. Это главный артефакт, связывающий разработку и UAT: QA пишет test cases на основе acceptance criteria, и UAT проверяет их выполнение. Стандартный формат — Given/When/Then (Gherkin, BDD). Например, для user story «Абонент может пополнить баланс с карты»: «Given: абонент с активным договором и балансом 100 ₽. When: абонент инициирует пополнение на 500 ₽ с валидной карты. Then: баланс становится 600 ₽, создаётся запись о платеже, отправляется SMS-подтверждение». Хорошие критерии конкретные, проверяемые, атомарные, покрывают happy path и крайние случаи, согласованы с бизнесом до начала разработки.

**6. Напиши acceptance criteria для user story «Абонент может приостановить действие договора».**

> Несколько критериев в формате Given/When/Then:
>
> 1. Happy path:
>    - Given: абонент с активным договором и нулевой задолженностью
>    - When: абонент подаёт заявку на приостановку через личный кабинет
>    - Then: договор переходит в статус «приостановлен», абонентская плата не начисляется, отправляется подтверждение на email
>
> 2. С задолженностью:
>    - Given: абонент с активным договором и задолженностью 500 ₽
>    - When: абонент пытается подать заявку на приостановку
>    - Then: система отклоняет заявку с сообщением «погасите задолженность», заявка не создаётся
>
> 3. Срок приостановки:
>    - Given: договор в статусе «приостановлен» более 90 дней
>    - When: наступает 91-й день
>    - Then: система автоматически возобновляет договор и отправляет уведомление абоненту
>
> 4. Восстановление:
>    - Given: договор в статусе «приостановлен» менее 90 дней
>    - When: абонент подаёт заявку на возобновление
>    - Then: договор возвращается в статус «активен», абонентская плата начисляется с даты возобновления

**7. В чём разница между severity и priority? Приведи пример, когда они не совпадают.**

> Severity — техническая оценка влияния дефекта на систему: Critical, High, Medium, Low. Priority — бизнес-оценка, как быстро нужно исправить: P1, P2, P3, P4. Они не всегда совпадают. Опечатка на главной странице банка (Low severity, потому что не влияет на функциональность) — P1, потому что падает доверие клиентов и бренд страдает. Редкий баг в админке при определённой последовательности действий (High severity, потому что админка падает) — P3, потому что есть workaround (перезагрузить страницу) и администраторов мало. В UAT важно различать: пользователь репортит дефект — это не значит, что он critical. BA вместе с QA и разработчиком triage'ит дефекты по обоим параметрам.

**8. Что такое sign-off и как ты его получаешь?**

> Sign-off — формальное одобрение бизнесом готовности системы к релизу. Процесс: по завершении UAT BA собирает результаты — сколько test cases passed/failed, какие дефекты открыты, какие закрыты. BA и QA проводят triage: какие дефекты блокируют релиз, какие можно отложить. BA презентует результаты бизнес-заказчику, объясняет риски. Бизнес принимает решение: sign-off (да, в прод), conditional sign-off (да, но с условием исправить X в Y-сроке), или no-go (возврат на доработку). Решение фиксируется в документе или тикет-системе. Conditional sign-off — частый случай: бизнес готов релизить с известными issues, если они будут исправлены в ближайшем patch.

**9. Сценарий: за день до релиза UAT провален — critical дефект в платёжном flow. Что делаешь?**

> Сначала triage вместе с QA и разработчиком: действительно ли дефект critical (блокирует ключевую функцию) или его можно обойти. Если critical — готовлю для бизнеса clear summary: что не работает, какое влияние, какие варианты. Варианты: 1) отложить релиз и исправить — если дефект затрагивает критичную функциональность, без которой релиз не имеет смысла; 2) релизить без платёжного flow с коммуникацией «платежи временно недоступны» — если остальная функциональность самодостаточна; 3) релизить с workaround (например, через старый интерфейс) — если он приемлем для пользователей. Решение принимает бизнес на основе моего анализа, не я. Если выбрали «отложить» — пересогласую сроки, координирую исправление, повторный UAT только на затронутую область. Главное — не скрывать проблему, а дать бизнесу данные для решения.

**10. Как ты готовишь тестовые данные для UAT?**

> Принципы: данные должны быть реалистичными, репрезентативными, но не реальными prod-данными (если прод-данные — то anonymизированные). Готовлю несколько наборов: happy path (типичный абонент), edge cases (минимальный/максимальный баланс, нулевой, граничные даты), негативные (заблокированный абонент, истёкший договор). Если система интегрируется с внешними — моки или sandbox-данные. Окружение UAT должно быть отдельным от dev/test, чтобы тесты не мешали разработке и наоборот. Важно синхронизировать тестовые данные между интеграциями: если абонент в CRM имеет ID 123, он должен быть тем же в биллинге и OSS. Если данные устарели — обновляю перед UAT. В telco-проектах часто готовлю «тестовые паспорта/ИНН» — выдуманные, но валидные по формату, чтобы пройти проверки.

**11. Бизнес-пользователь говорит «мне не нравится, как это работает», но формально это соответствует требованиям. Что делаешь?**

> Это классическая ситуация, и она показывает разрыв между формальными требованиями и реальной потребностью. Сначала уточняю, что именно не нравится — копаю до конкретики: «не нравится UI», «не нравится последовательность шагов», «не хватает функции X». Дальше — два пути. Если это правка в пределах user story, которую мы упустили при сборе требований — это наш недочёт, добавляем в backlog как enhancement, обсуждаем с командой, входит ли в этот релиз. Если это новое требование, которого не было в scope — заводим как отдельную user story для следующего релиза. Глобальный вывод: UAT выявил пробел в elicitation, и нужно разобраться, почему это не всплыло раньше — может, не тех людей опрашивали, может, не те вопросы задавали. Это материал для ретроспективы.

**12. Как ты убеждаешь бизнес-пользователей уделить время UAT?**

> Это постоянная боль — бизнес-пользователи заняты своей работой, UAT для них «дополнительная нагрузка». Что работает: 1) договариваться о времени заранее, ещё на этапе планирования релиза — чтобы календарь был забронирован; 2) получить поддержку спонсора проекта, чтобы он выделил людей; 3) сделать UAT максимально простым для них — готовые test cases, понятные инструкции, тестовые данные под рукой; 4) выделить «буфер» — два дня UAT, чтобы один день они точно были свободны; 5) проводить UAT-сессии совместно — BA сидит рядом, помогает, фиксирует результаты, чтобы пользователь не тратил время на бюрократию; 6) показать ценность: «ваше участие сейчас сэкономит вам месяцы работы с неудобной системой в проде». Если бизнес категорически не может выделить людей — BA сам проходит UAT от их имени, но это компромисс, и его нужно явно зафиксировать как риск.

### 4. Типичные ошибки и на что смотрят интервьюеры

**Частые ошибки кандидатов:**

- Путают severity и priority.
- Не могут назвать entry/exit criteria UAT.
- Считают UAT и functional testing одним и тем же.
- Пишут acceptance criteria без крайних случаев.
- Не знают формат Given/When/Then.
- На сценарий «UAT провален перед релизом» отвечают «исправим и релизим», не разбирая вариантов.
- Не различают test case и test scenario.

**Сильный vs слабый ответ:**

| Что спрашивают | Слабый ответ | Сильный ответ |
|---|---|---|
| Чем UAT отличается от функционального? | «UAT делает пользователь». | Функциональное — про соответствие спеке, делает QA. UAT — про бизнес-ценность, делает пользователь. Функциональное может пройти, а UAT — нет, если спека неточная. |
| Что такое severity и priority? | «Это одно и то же». | Severity — техническая оценка, priority — бизнес. Приводит пример несовпадения (опечатка на главной банка: Low severity, P1). |
| UAT провален перед релизом | «Исправим и релизим». | Triage, оценка влияния, варианты (отложить/релизить без части/с workaround), решение принимает бизнес на основе анализа. |

**На что смотрит интервьюер:**

- Различает ли кандидат виды тестирования и место UAT в цепочке.
- Умеет ли писать acceptance criteria в формате Given/When/Then с крайними случаями.
- Понимает ли разницу между severity и priority, с примером несовпадения.
- Способен ли triage'ить дефекты и презентовать результаты бизнесу.
- Умеет ли вести переговоры при провале UAT.

> **Телеком-акцент:** в телекоме UAT критичен, потому что ошибки в биллинге стоят денег напрямую — неверный тариф, незачисленный платёж, лишняя блокировка. Бизнес-пользователи UAT в телекоме — это обычно сотрудники отделов обслуживания, которые знают процессы изнутри. BA должен иметь под рукой реальные сценарии: «абонент меняет тариф», «абонент переносит номер», «блокировка при отрицательном балансе», «восстановление после оплаты». Если доведётся рассказывать про опыт — упомяни, что знаешь телеком-сценарии и понимаешь цену ошибки в биллинге.

## Тема 7. Требования (Requirements)

### 1. Теория

#### 1.1. BABOK и классификация требований

BABOK (Business Analysis Body of Knowledge) — методология бизнес-анализа от IIBA. В ней требования делятся на типы по уровню детализации и аудитории. Классификация BABOK — самый частый вопрос на интервью по требованиям.

Четыре основных типа требований по BABOK:

1. **Business requirements (бизнес-требования)** — зачем бизнесу это нужно, какую цель решаем. Высокий уровень, пишутся для топ-менеджмента и спонсоров. Пример: «Увеличить удержание абонентов B2C-сегмента на 5% к концу года за счёт автоматического напоминания об оплате».

2. **Stakeholder requirements (требования стейкхолдеров)** — что нужно конкретным группам пользователей и заинтересованным лицам. Промежуточный уровень. Пример: «Менеджер по работе с клиентами должен видеть в CRM историю платежей абонента за последние 12 месяцев».

3. **Solution requirements (требования к решению)** — как система должна себя вести, чтобы удовлетворить бизнес- и stakeholder-требования. Делятся на:
   - **Functional (функциональные)** — что система делает: функции, поведение, данные. «Система должна отправлять SMS-уведомление за 3 дня до окончания оплаченного периода».
   - **Non-functional (нефункциональные)** — как система делает: производительность, безопасность, доступность, usability. «Система должна обрабатывать платёж за < 2 сек в 95% случаев».

4. **Transition requirements (переходные требования)** — что нужно для перехода от текущего состояния к целевому: миграция данных, обучение пользователей, разовый импорт. После перехода эти требования теряют актуальность.

На интервью важно различать эти типы и уметь классифицировать конкретное требование.

#### 1.2. Техники elicitation (сбора требований)

Elicitation — процесс выявления требований. Не «сбор» (requirements gathering) — это слово подразумевает, что требования уже существуют и их нужно просто собрать. На практике требования формируются в процессе elicitation.

Основные техники:

- **Interviews (интервью)** — один на один с стейкхолдером. Глубоко, но медленно; хорошо для первичного понимания.
- **Workshops (воркшопы)** — групповая сессия с несколькими стейкхолдерами. Быстро, но требует фасилитации; хорошо для согласования конфликтующих требований.
- **Brainstorming (мозговой штурм)** — генерация идей без критики. Хорошо для инноваций и поиска новых решений.
- **Document analysis (анализ документов)** — изучение существующих спецификаций, регламентов, отчётов. Хорошо для систем, где есть legacy-документация.
- **Observation (наблюдение)** — наблюдение за пользователями в их реальной работе. Хорошо для tacit knowledge — того, что пользователи делают, но не могут объяснить.
- **Prototyping (прототипирование)** — быстрый набросок UI или функциональности для проверки идей. Хорошо для визуализации абстрактных требований.
- **Surveys/questionnaires (опросы)** — анкеты для большой аудитории. Хорошо для количественных данных, плохо для глубинного понимания.
- **Focus groups (фокус-группы)** — групповое обсуждение с представителями целевой аудитории.
- **Interface analysis (анализ интерфейсов)** — анализ существующих систем и их интеграций.

На практике BA использует 3-5 техник в одном проекте, комбинируя их. Универсальной техники нет — каждая под свою задачу.

#### 1.3. Документация требований

**BRD (Business Requirements Document):**

- Высокий уровень, для топ-менеджмента и спонсоров.
- Содержит: бизнес-проблема, цели, обоснование (business case), scope, стейкхолдеры, high-level требования, ограничения, риски.
- Используется в Waterfall и крупных проектах. В Agile редко — заменяется на vision document.

**FRD (Functional Requirements Document):**

- Детальные функциональные требования для разработчиков.
- Содержит: use cases, функциональные спецификации, требования к данным, требования к интерфейсам.
- Используется в Waterfall и enterprise. В Agile — заменяется на user stories + acceptance criteria.

**User stories (пользовательские истории):**

- Короткий формат: «Как [роль], я хочу [действие], чтобы [ценность]».
- Agile-формат, заменяет BRD/FRD в большинстве современных проектов.
- К каждой user story прилагаются acceptance criteria.
- Хороши для обсуждения с бизнесом и оценки; не заменяют детальные use cases для сложной логики.

**Use cases (прецеденты):**

- Детальное описание сценария: актор, предусловия, основной flow, альтернативные flow, исключения, постусловия.
- Хорошо для сложной логики с ветвлениями.
- Используются в enterprise и в дополнение к user stories для критичных сценариев.

Когда что:

- BRD — для обоснования проекта перед спонсорами.
- FRD — для крупных Waterfall-проектов с фиксированным scope.
- User stories — для Agile-команд, итеративной разработки.
- Use cases — для сложной логики и критичных сценариев внутри любого подхода.

#### 1.4. Requirements traceability matrix (RTM)

RTM — таблица, связывающая требования между уровнями и с артефактами реализации. Строки — требования, столбцы — связи с бизнес-целями, user stories, тест-кейсами, кодом.

Зачем нужна RTM:

- **Coverage:** убедиться, что каждое бизнес-требование покрыто user story и тест-кейсом.
- **Impact analysis:** при изменении требования понять, какие user stories и тесты затронуты.
- **Origin tracking:** при user story понять, какое бизнес-требование за ней стоит (или не стоит — orphan).
- **Compliance:** для регулируемых отраслей (банки, телеком с персональными данными) — обязательна.

В Agile-проектах RTM поддерживается в Jira/Confluence через links между эпиками, story и тест-кейсами. В Waterfall — отдельный документ.

#### 1.5. Приоритизация требований

**MoSCoW:**

- **Must have** — обязательно для релиза. Без этого релиз не имеет смысла.
- **Should have** — важно, но не критично. Можно отложить на следующий релиз при необходимости.
- **Could have** — желательно, если есть время и ресурсы.
- **Won't have** — явно не входит в этот релиз.

MoSCoW прост, понятен бизнесу, и чаще всего используется. Минус — субъективность, всё легко назвать «Must».

**Kano model:**

Анализ требований по тому, как они влияют на удовлетворённость пользователя:

- **Basic (базовые)** — ожидаемые по умолчанию. Если их нет — пользователь недоволен; если есть — не замечает. Пример: «приложение не падает».
- **Performance (производительные)** — чем больше, тем лучше. Линейная зависимость удовлетворённости. Пример: «скорость загрузки».
- **Excitement (волнующие)** — неожиданные приятные фичи. Если их нет — пользователь не расстроен; если есть — в восторге. Пример: персональные рекомендации.
- **Indifferent (безразличные)** — пользователю всё равно.
- **Reverse (обратные)** — чем больше, тем хуже. Пример: лишние поля в форме.

Kano помогает понять, какие требования реально двигают удовлетворённость, а какие — просто ожидаемая база. Хорошо работает для продуктовых проектов.

**Другие техники:**

- **Priority poker** — голосование стейкхолдеров.
- **WSJF (Weighted Shortest Job First)** — из SAFe, учитывает стоимость задержки.
- **100-point method** — каждому стейкхолдеру 100 баллов, распределяет по требованиям.

#### 1.6. Управление изменениями требований и scope creep

Scope creep (расползание scope) — постепенное неконтролируемое добавление требований в проект. Главная причина срыва сроков и бюджетов.

Причины scope creep:

- Нечёткий изначальный scope.
- Изменение приоритетов бизнеса в ходе проекта.
- Новые стейкхолдеры, приходящие с новыми требованиями.
- «Забытые» требования, всплывающие поздно.
- Слабой контроль change request'ов.

Превентивные меры:

- Чёткий scope statement в начале проекта.
- Change request process: любое новое требование проходит через оценку impact'а и одобрение change control board.
- Prioritization (MoSCoW, Kano) — новые требования попадают в Could/Won't, а не в Must.
- Регулярная коммуникация с заказчиком о trade-off'ах scope vs сроки.
- Timeboxing — фиксируем дату релиза, scope варьируется.

Управление изменениями:

1. Логирование change request'а.
2. Оценка impact'а: на какие артефакты влияет, сколько времени добавляет, какие риски.
3. Решение: accept (входим в scope), defer (откладываем), reject (отклоняем с обоснованием).
4. Коммуникация решения всем заинтересованным.
5. Обновление RTM, бэклога, планов.

#### 1.7. Противоречивые требования

Частая ситуация: стейкхолдер A хочет «сделать платёж в один клик», стейкхолдер B (security) — «двухфакторная аутентификация на каждый платёж». Противоречие.

Алгоритм разрешения:

1. Выявить корень противоречия — какие бизнес-цели за каждым требованием. A хочет конверсию, B хочет безопасность.
2. Понять, можно ли удовлетворить обе цели компромиссным решением. Например: «один клик для платежей до 1000 ₽, 2FA для больших».
3. Если компромисс невозможен — эскалировать на спонсора проекта. Решение принимает он, не BA. BA готовит данные: pros/cons каждого варианта, риски, impact на бизнес-цели.
4. Зафиксировать решение и его обоснование. Чтобы через полгода не было «а почему мы так сделали?».
5. Обновить требования.

BA не «решает» противоречие, а фасилитирует процесс решения. Финальное решение — за бизнесом.

### 3. Практика

**1. Назови типы требований по BABOK и объясни разницу.**

> По BABOK требования делятся на четыре типа. Business requirements — зачем бизнесу это нужно, какую цель решаем. Высокий уровень, для топ-менеджмента. Пример: «увеличить удержание абонентов на 5%». Stakeholder requirements — что нужно конкретным группам пользователей и заинтересованным лицам. Промежуточный уровень. Пример: «менеджер CRM должен видеть историю платежей за 12 месяцев». Solution requirements — как система должна себя вести, делятся на functional (что делает: «отправлять SMS за 3 дня до окончания») и non-functional (как делает: «обрабатывать платёж за < 2 сек в 95% случаев»). Transition requirements — что нужно для перехода от текущего к целевому: миграция данных, обучение, разовый импорт. После перехода теряют актуальность. На интервью часто ловят на том, что кандидат путает functional и non-functional — это разные типы внутри solution requirements.

**2. Чем functional требования отличаются от non-functional? Приведи примеры.**

> Functional — что система делает: функции, поведение, данные. «Система должна отправлять SMS-уведомление за 3 дня до окончания оплаченного периода», «система должна позволять абоненту менять тариф через личный кабинет». Non-functional — как система делает: производительность, безопасность, доступность, usability. «Система должна обрабатывать платёж за < 2 сек в 95% случаев», «система должна соответствовать 152-ФЗ по обработке персональных данных», «UI должен быть на русском и английском». Functional описывает поведение, non-functional описывает качества. Один functional может поддерживаться разными non-functional: «платёж» может быть мгновенным или за 5 секунд, безопасным или нет, available 99.9% или 95%.

**3. Какие техники elicitation ты знаешь? Когда какую применяешь?**

> Основные техники: interviews (один на один со стейкхолдером — глубоко, для первичного понимания), workshops (групповая сессия — быстро, для согласования конфликтов), brainstorming (генерация идей без критики — для инноваций), document analysis (анализ регламентов и спецификаций — для legacy), observation (наблюдение за пользователями — для tacit knowledge, того, что не могут объяснить), prototyping (быстрый набросок UI — для визуализации абстрактных требований), surveys (анкеты — для количественных данных на большой аудитории). На практике комбинирую 3-5 техник в проекте. Например, в начале — interviews с ключевыми стейкхолдерами, потом workshop для согласования, потом prototyping для проверки. Универсальной техники нет — каждая под свою задачу.

**4. Чем BRD отличается от FRD? Что используешь в Agile?**

> BRD — Business Requirements Document, высокого уровня, для спонсоров и топ-менеджмента. Содержит бизнес-проблему, цели, обоснование, scope, стейкхолдеров, high-level требования. FRD — Functional Requirements Document, детальные функциональные требования для разработчиков. Содержит use cases, спецификации, требования к данным. В Agile ни BRD, ни FRD в классическом виде не используются — заменяются на vision document (короткий high-level документ) + user stories с acceptance criteria в бэклоге. Use cases иногда применяют дополнительно для критичных сложных сценариев. Если у меня Agile-проект — у меня есть product vision и бэклог user stories; если Waterfall с фиксированным scope — BRD + FRD.

**5. Что такое user story и в каком формате её пишут?**

> User story — короткий формат описания требования в Agile. Стандартный формат: «Как [роль], я хочу [действие], чтобы [ценность]». Пример: «Как абонент B2C, я хочу видеть остаток трафика в личном кабинете, чтобы планировать использование до конца месяца». К каждой user story прилагаются acceptance criteria — условия, при которых story считается выполненной. Хорошая user story: независимая (I), обсуждаемая (N), ценная (V), оцениваемая (E), небольшая (S), тестируемая (T) — критерии INVEST. Плохо: «Как разработчик, я хочу таблицу X, чтобы хранить данные» — это техническая задача, а не user story, у неё нет бизнес-ценности. В Agile user stories заменяют BRD/FRD, но для сложной логики используются дополнительно use cases.

**6. Что такое MoSCoW и в чём его минусы?**

> MoSCoW — метод приоритизации требований: Must have (обязательно для релиза), Should have (важно, но можно отложить), Could have (желательно при наличии времени), Won't have (явно не входит). Простой, понятный бизнесу, чаще всего используется. Минусы: субъективность — всё легко назвать «Must», и в итоге 80% требований оказываются Must, что обесценивает приоритизацию. Лечится жёстким квотированием: например, не более 40% Must, 30% Should, 20% Could, 10% Won't. Ещё минус: MoSCoW не учитывает стоимость реализации — дешёвый Could может быть полезнее дорогого Must. Поэтому MoSCoW часто комбинируют с оценкой effort: priority vs effort matrix. Альтернативы: Kano (по влиянию на удовлетворённость), WSJF (из SAFe, учитывает стоимость задержки).

**7. Объясни Kano model.**

> Kano — модель приоритизации требований по влиянию на удовлетворённость пользователя. Пять категорий. Basic — ожидаемые по умолчанию: если их нет — недоволен; если есть — не замечает. Пример: «приложение не падает». Performance — чем больше, тем лучше, линейная зависимость. Пример: «скорость загрузки». Excitement — неожиданные приятные фичи: если нет — не расстроен; если есть — в восторге. Пример: персональные рекомендации. Indifferent — пользователю всё равно. Reverse — чем больше, тем хуже. Пример: лишние поля в форме. Kano помогает понять, какие требования реально двигают удовлетворённость (Performance, Excitement), а какие — просто ожидаемая база (Basic). Бизнес часто хочет «добавить фич», не понимая, что без Basic-базы Performance и Excitement не работают. Kano хорошо работает для продуктовых проектов, где удовлетворённость — ключевая метрика.

**8. Что такое requirements traceability matrix и зачем она нужна?**

> RTM — таблица, связывающая требования между уровнями и с артефактами реализации. Строки — требования, столбцы — связи с бизнес-целями, user stories, тест-кейсами, кодом. Зачем нужна: coverage — убедиться, что каждое бизнес-требование покрыто user story и тест-кейсом; impact analysis — при изменении требования понять, какие story и тесты затронуты; origin tracking — при user story понять, какое бизнес-требование за ней стоит (или не стоит — orphan); compliance — для регулируемых отраслей (банки, телеком с персональными данными) обязательна. В Agile RTM поддерживается в Jira/Confluence через links между эпиками, story и тест-кейсами. В Waterfall — отдельный документ. Минус — поддержание в актуальном состоянии требует дисциплины, и без него RTM быстро устаревает.

**9. Что такое scope creep и как его предотвращать?**

> Scope creep — постепенное неконтролируемое добавление требований в проект. Главная причина срыва сроков и бюджетов. Причины: нечёткий изначальный scope, изменение приоритетов бизнеса, новые стейкхолдеры с новыми требованиями, «забытые» требования, слабой контроль change request'ов. Превентивные меры: чёткий scope statement в начале проекта; change request process — любое новое требование проходит через оценку impact'а и одобрение change control board; prioritization — новые требования попадают в Could/Won't, а не в Must; регулярная коммуникация с заказчиком о trade-off'ах scope vs сроки; timeboxing — фиксируем дату релиза, scope варьируется. На практике в Agile scope creep менее опасен, потому что есть естественный механизм — новый requirement попадает в бэклог и приоритизируется, а не молча добавляется. В Waterfall с фиксированным scope — scope creep критичен.

**10. Сценарий: два стейкхолдера дают противоречивые требования. Как поступишь?**

> Сначала выявляю корень противоречия — какие бизнес-цели за каждым требованием. Например: стейкхолдер A хочет «платёж в один клик» (цель: конверсия), стейкхолдер B (security) — «2FA на каждый платёж» (цель: безопасность). Дальше пытаюсь найти компромисс, удовлетворяющий обе цели: «один клик для платежей до 1000 ₽, 2FA для больших». Если компромисс невозможен — эскалирую на спонсора проекта. Решение принимает он, не я. Я готовлю данные: pros/cons каждого варианта, риски, impact на бизнес-цели. Решение фиксирую с обоснованием, чтобы через полгода не было «а почему мы так сделали?». Обновляю требования. BA не «решает» противоречие, а фасилитирует процесс решения. Финальное решение — за бизнесом, и это важно, потому что BA не несёт ответственности за бизнес-последствия выбора.

**11. Бизнес приходит с требованием «сделайте как у конкурента X». Как реагируешь?**

> «Как у конкурента» — не требование, это сигнал, что есть неудовлетворённая потребность, но она не сформулирована явно. Сначала уточняю, что именно у конкурента нравится: UI? функциональность? скорость? цена? Копировать конкурента вслепую — плохая идея, потому что у него другая бизнес-модель, другая аудитория, другие ограничения. Дальше копаю до бизнес-потребности: «какую проблему пользователя решает эта фича у конкурента?». Когда понятна потребность — можно придумать решение, которое решит её лучше или дешевле, чем копирование. Если бизнес настаивает на копировании — оцениваю effort и честно говорю, сколько это будет стоить и сколько займёт, предлагаю альтернативы. Часто после оценки бизнес пересматривает приоритет. Главное — не отказывать в лоб, а переводить разговор от «фичи конкурента» к «потребности пользователя».

**12. Что такое INVEST в контексте user stories?**

> INVEST — критерии качественной user story: Independent (независимая — можно реализовать и релизнуть без других stories), Negotiable (обсуждаемая — не задание разработчику, а тема для обсуждения), Valuable (ценная — приносит бизнес-ценность), Estimable (оцениваемая — команда может оценить effort), Small (небольшая — реализуется за один спринт), Testable (тестируемая — есть чёткие acceptance criteria). Пример нарушения INVEST: «Как разработчик, я хочу таблицу X с полями A, B, C, чтобы хранить данные» — нарушено Valuable (нет бизнес-ценности), Negotiable (задание, а не тема), Testable (нет acceptance criteria). Это техническая задача, а не user story. INVEST — простой чек-лист для BA при написании stories. Если story не проходит INVEST — нужно её переработать.

### 4. Типичные ошибки и на что смотрят интервьюеры

**Частые ошибки кандидатов:**

- Не могут назвать все типы требований по BABOK.
- Путают functional и non-functional.
- Считают elicitation = «сбор» требований, не понимая, что требования формируются в процессе.
- Называют MoSCoW и Kano, но не могут объяснить минусы MoSCoW.
- На сценарий с противоречивыми требованиями сразу предлагают «своё» решение, вместо того чтобы эскалировать бизнесу.
- Не знают INVEST для user stories.
- Считают user story и use case одним и тем же.

**Сильный vs слабый ответ:**

| Что спрашивают | Слабый ответ | Сильный ответ |
|---|---|---|
| Какие типы требований знаешь? | «Функциональные и нефункциональные». | Называет все четыре по BABOK: business, stakeholder, solution (functional + non-functional), transition. Приводит примеры. |
| Что такое MoSCoW? | «Must, Should, Could, Won't». | Объясняет, плюс минусы (субъективность, всё становится Must), и как лечить (квотирование). Упоминает альтернативы (Kano, WSJF). |
| Противоречивые требования | «Я бы выбрал то, что кажется правильным». | Сначала ищет корень (бизнес-цели), потом компромисс, потом эскалация на спонсора. BA фасилитирует, не решает. |

**На что смотрит интервьюер:**

- Знает ли кандидат классификацию требований по BABOK.
- Различает ли functional и non-functional, с примерами.
- Понимает ли, что elicitation — это активный процесс, а не «сбор».
- Умеет ли приоритизировать не одним методом, а несколькими, и знает их минусы.
- Способен ли фасилитировать разрешение конфликтов требований, не подменяя собой бизнес.
- Знает ли INVEST и применяет ли при написании user stories.

> **Телеком-акцент:** в телекоме требования часто регламентированы — тарифы, условия обслуживания, обработка персональных данных (152-ФЗ), правила блокировки. BA должен уметь работать с этим контекстом: ссылаться на конкретные пункты регламентов в требованиях, выделять compliance-требования как отдельный класс, вести RTM для аудиторов. Если доведётся рассказывать про опыт — упомяни, что знаешь специфику телеком-требований: биллинговые циклы, тарифные планы, CDR-обработка, SLA-требования к услугам. Это сразу поднимает уровень кандидата в глазах интервьюера.

## Итоговый чек-лист перед интервью

Перед собеседованием по каждому из 7 разделов пробегись мысленно по 3–5 ключевым вещам, которые с высокой вероятностью спросят.

**1. SQL, BI-аналитика**
- Типы JOIN (INNER/LEFT/RIGHT/FULL/CROSS) и когда каждый выбирать.
- Оконные функции (ROW_NUMBER, RANK, LAG/LEAD) — чем отличаются от GROUP BY.
- Порядок выполнения SQL (FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY).
- OLTP vs OLAP, звезда vs снежинка, ETL vs ELT.
- Принципы дизайна дашбордов (один дашборд — одна аудитория, Z-чтение, минимум цветов).
- *Телеком-акцент:* ARPU, churn rate, CDR — упомянуть обязательно.

**2. API**
- REST-ограничения (особенно statelessness), HTTP-методы и идемпотентность.
- 401 vs 403 — самое частое «отличите».
- Аутентификация: API key / OAuth2 / JWT — чем отличаются.
- Idempotency-Key для платёжных операций.
- SOAP vs REST vs GraphQL — сравнительная таблица.
- *Телеком-акцент:* BSS vs OSS, синхронные (активация услуги) vs асинхронные (выгрузка CDR) API.

**3. Apache Kafka, gRPC, RabbitMQ**
- Kafka как лог (replay, retention) vs RabbitMQ как очередь (push, ack-удаление).
- Партиция и ключ партицирования — для порядка событий одного абонента.
- At-least-once + идемпотентный consumer вместо exactly-once.
- Outbox pattern — что решает и как.
- Когда gRPC, когда REST, когда Kafka.
- *Телеком-акцент:* биллинг как producer событий, несколько consumer'ов.

**4. Микросервисная архитектура**
- Монолит vs микросервисы — компромисс, не «лучше».
- Bounded context (DDD) — основа для разбиения на сервисы.
- Database-per-service, API Gateway, Circuit Breaker, Saga (choreography vs orchestration).
- Eventual vs strong consistency — когда каждая.
- Роль BA: контракты, события, саги, управление ожиданиями.
- *Телеком-акцент:* типовой набор BSS+OSS сервисов, цикл Order→Provisioning→Billing→Notification.

**5. BPMN, UML, C4, ERD**
- BPMN: пулы/дорожки, события, шлюзы (XOR/AND/OR).
- UML: use case, sequence, activity, class — когда каждый.
- C4: 4 уровня (Context, Container, Component, Code) и аудитория каждого.
- ERD: сущности, атрибуты, кратность (1:1, 1:N, N:M), нотации (Crow's Foot, Chen).
- Выбор диаграммы под аудиторию: BPMN для бизнеса, C4 для архитекторов, sequence для разработчиков.
- *Телеком-акцент:* описать цикл «заявка → активация → биллинг» на разных уровнях.

**6. UAT**
- Место UAT в SDLC (unit → integration → system → UAT → релиз).
- Entry/exit criteria, sign-off.
- Acceptance criteria в формате Given/When/Then.
- Severity vs priority — с примером несовпадения.
- Роль BA vs QA в UAT.
- *Телеком-акцент:* цена ошибки в биллинге, тестовые сценарии (смена тарифа, перенос номера, блокировка).

**7. Требования**
- 4 типа по BABOK: business, stakeholder, solution (functional + non-functional), transition.
- Elicitation ≠ сбор: требования формируются в процессе.
- Документация: BRD, FRD, user stories, use cases — когда что.
- Приоритизация: MoSCoW (с минусами), Kano, WSJF.
- Scope creep и управление изменениями; INVEST для user stories.
- *Телеком-акцент:* регламентированные требования, 152-ФЗ, RTM для аудиторов, биллинговые циклы.

**Общие советы:**
- Отвечай структурно: «Это X, потому что Y. Пример из моего опыта...».
- Если не знаешь точный ответ — рассуждай вслух, интервьюер оценивает ход мысли.
- Не бойся сказать «не знаю, но думаю, что...» — это лучше, чем уверенно говорить неправду.
- Подготовь 2-3 истории из своего опыта на каждый раздел — конкретика сильнее теории.
- Перед интервью прогони себя по этому чек-листу — это займёт 30 минут и снимет 80% стресса.

Удачи на собеседовании!
